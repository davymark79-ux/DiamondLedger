# Diamond Ledger — Baseball Sim

A from-scratch baseball simulation engine + React UI ("Diamond Ledger"). Plain JS (not TypeScript), Vite + React + Tailwind, `oxlint` for linting. Now a git repository (initialized partway through the build) — `git log` has real history from that point forward, but this file and `diamond-ledger-design-docs/` remain the primary record for design intent and the reasoning behind decisions.

**Design docs**: `diamond-ledger-design-docs/` — `README.md` is the index. These are the source of truth for *intended* mechanics. The actual code sometimes diverges from them in deliberate, flagged ways (documented inline in the relevant files and summarized below) — usually because a doc leaves an algorithm/exact-value unspecced, or depends on a system that doesn't exist yet.

**Running it**: `npm run dev` (Vite dev server). No automated test framework — verification is via the `npm run validate:*` scripts (see below) plus manual browser checks.

## Architecture / layering convention

- **`src/models/`** — schema + generation only. No simulation logic.
  - `Player.js`, `Team.js`, `League.js`, `constants.js` — core schema. Ratings are 20-80 scale, three-layer (`current` / `truePotential` / `scoutedPotential`).
  - `generation/` — seeded generators. `playerGenerator.js` has **two distinct modes**: `generatePlayer()` builds HS/pre-draft prospects (age 17-18, only 30-70% of true potential realized — raw, unfinished talent, position picked from a weighted pool) and `generateEstablishedPlayer()` builds active-roster-ready players (age 21-37, 85-100% of true potential realized, **requires an explicit `position`** — no random draw, since real rosters need guaranteed position coverage). `random.js` (`createRng`, `randomInRange`, `pickWeighted`, `pick`, `gaussianRandom`) is a deterministic mulberry32 PRNG — `rng` is **always** an explicit passed-in parameter throughout the whole codebase, never an implicit `Math.random()`.
  - `seed/` — `leagueSeed.js` (the real, locked-in 50-team structure transcribed from `league-structure.md`: 30 MLB1 teams in 3 divisions + 20 MLB2 teams in 2 divisions, each division mixing Foundry-league and Exchange-league teams roughly half-and-half), `rosterSeed.js` (attaches real 26-man rosters to those teams).
- **`src/engine/`** — simulation mechanics that read/transform Player/Team objects. Deliberately non-mutating (`growthModel.js`'s explicit "returns a new object" convention) — the one exception is `engine/season.js`'s external accumulator `Map`s (standings, rotation index, injury status), which are caller-owned state, not mutations of the Player/Team objects themselves.
- **`src/data/`** — UI-facing data. `realLeague.js` computes the real 50-team league + initial rosters/managers once at module load with a fixed seed (identity data that never changes season-to-season: city/nickname/tier/division/marketSize/ownership). `season.js` used to be a similar eager, computed-once singleton, but as of section 20 it's the **live, advanceable, localStorage-persisted season state** instead — it still only computes once per page load (or once ever, if a save exists), just no longer frozen forever; see section 20 for why and `src/state/LeagueStateContext.jsx` for the React wiring that makes it live. `hallOfFame.js` is a genuinely frozen static-seed precedent (a one-time-run precomputed snapshot script, see section 18) — deliberately **not** wired to the live season state; it always shows the same hypothetical-future class regardless of what season the live app is actually on. `gameContext.js` (venue/attendance/game-time flavor for `BoxScore.jsx`, see section 5) is a small `Date.now()`-seeded cosmetic derivation, unrelated to season progression. `mockData.js` (old placeholder data that pre-dated the real engine) is **gone** — every page reads real data; nothing in `src/` imports it anymore.
- **`src/state/`** — React Context/hook wiring for live app state (see section 20). Currently just `LeagueStateContext.jsx`. Thin by design: it holds state and exposes it, the actual state-transition logic lives in `data/season.js`/`engine/leagueProgression.js`.
- **`src/pages/`** — route components.

## Build order / current state

### 1. Schema — done
`Player` / `Team` / `League` + `constants.js`. Attribute groups: `HITTING_ATTRIBUTES`, `BASERUNNING_ATTRIBUTES`, `DEFENSE_ATTRIBUTES`, `PITCHING_ATTRIBUTES` (pitchers only), `MAKEUP_ATTRIBUTES` (`workEthic`, `durability`, `consistency`, `coachability`). `Player.injury` — `null` when healthy, otherwise `{type, severity, gamesRemaining, sustainedGameNumber}`. Note: this field documents the *shape*, but the **authoritative** injury tracking lives externally in `engine/season.js`'s `injuryStatusById` Map, not by mutating this field on the shared `realLeague.js` Player objects (keeps that singleton pure).

### 2. Plate-appearance engine — done
`plateAppearance.js` + `plateAppearanceConstants.js`, validated via `npm run validate:sim` against real modern-MLB per-PA rate stats (`BASE_RATES`, `BASE_BABIP` are anchored to ~.248/.312/.410-ish league averages). **Do not inflate these constants** to fix an aggregate run-environment problem elsewhere in the pipeline — tried once, it corrupted the anchored neutral-matchup baseline; the real fix belonged elsewhere (see Calibration notes).

### 3. Full game loop — done
`game.js` orchestrates: baserunning (`baserunning.js`, includes double plays and sac flies), pitcher fatigue/times-through-the-order/bullpen management (`pitcherFatigue.js` + `timesThroughOrder.js` → `pitcherDegradation.js`; `pitchingChanges.js` decides pulls and next-pitcher), position-player substitutions (`hitterChanges.js` — pinch-hit / defensive-replacement / pinch-run, each now with a no-quality-gate `selectEmergency*` variant for injuries), per-game "form" consistency (`consistency.js` — `applyGamePerformance` / `applyPitcherGamePerformance` roll once per player per game; `withPerformanceModifiers` is the general "shift these ratings by a delta" primitive, reused by injuries and reserved for a future "playing hurt" mechanic), the ghost-runner extra-innings rule (`gameRules.js`, default off), box-score tracking (`boxScore.js` — batting/pitching lines, GIDP, RISP), pitcher decisions (`pitcherDecisions.js` — Win/Loss/Save/Hold/Blown-Save; a save requires the lead was *never* relinquished during the outing, not just checked at entry/exit), injury rolls (`injuries.js`, hooked into the per-PA/per-pitch loop), and position-player fatigue (`positionPlayerFatigue.js` — a per-game performance dip applied in `createSide()`, cross-game tracking owned by `engine/season.js`).

**Hard invariant, keep this pattern for any future substitution type**: `removedPlayerIds` (a `Set` per side) — once a player is subbed out for any reason, he can never be selected again. Enforced both structurally (spliced out of the pool array) *and* defensively (an explicit Set check inside every selector function). Stress-tested at scale (hundreds of games) before being trusted.

### 4. Growth Model + position reassignment — done
`growthModel.js` — period-over-period career development (`growth = baseline_growth + variance_roll`), calibrated so most players don't reach true potential. Extension-point hooks `locationModifier` (future college-prestige system) and `injuryImpact` (available for a future *development-period* injury penalty — **not** currently wired to the Injuries system that got built, which only handles in-game/season availability, not growth-period impact).
`positionReassignment.js` — fit-driven + aging-driven triggers only; org-depth and injury-driven triggers are still explicitly deferred (need Team-level roster depth charts / deeper Injuries integration than exists).
`reassignmentReaction.js` — Coachability-gated accept/refuse mechanic.
`development.js` composes all three. Validated via `npm run validate:growth`.

**Real bug found and fixed in section 20 (2026-07-21)**: `advanceDevelopmentPeriod`'s final `current` rating was never rounded (`Math.min(uncapped, rating.truePotential)`, no `Math.round`) — every other rating-setting call site in this engine (`playerGenerator.js`) explicitly rounds, but this one didn't. Invisible for the entire time Growth Model existed, because nothing in the live app ever actually called growth until section 20 wired `advanceOffseason` into a real "Simulate Next Season" action — the moment a real player went through a real growth period in the live UI, ratings started rendering as long floats (`53.30868216631135`). Fixed by wrapping the final value in `Math.round(...)`; re-validated `validate:growth` and the full suite, no regression.

### 5. Box Score UI — done, real rosters
`BoxScore.jsx` lets the user pick any two of the real 50 teams (two `<select>` dropdowns, each excluding whichever team is picked in the other, defaulting to two random distinct teams on load) and simulates a real game between their **real** rosters — `useLeagueState()`'s `buildMatchup(awayTeamId, homeTeamId, rng)` (moved from `data/season.js` into `src/state/LeagueStateContext.jsx` as of section 20, since it needs the *live* season state, not a static one) reuses `engine/season.js`'s own `buildGameSide`/`resolveAvailableRoster`/`resolveRestedRoster` (exported for exactly this reuse, the same functions the season loop itself calls per game), so this is subject to whatever season the app is currently on — a player currently on the shelf or fatigued is correctly unavailable/rested here too, and each team's real current manager's sliders apply. Each team starts `rotation[0]` (its de facto ace) — a standalone game has no rotation-index to cycle, unlike the season loop. "Simulate Again" re-runs the same two teams with a fresh rng; "Random Matchup" rerolls both teams. Shows a full real box score: stacked decision badges (W/L/S/H/BS — a pitcher can carry more than one, e.g. blown-save+win is a real combo), GIDP, substitution notes (including `injury`-type ones), lineup indentation for subs under whoever they replaced, and same-surname name disambiguation.

`src/data/gameContext.js` (replacing the deleted `simDemoRoster.js`, which used to *generate* a synthetic matchup — no longer needed now that real rosters exist) derives venue/attendance/game-time flavor from the real matchup's `marketSize` and the actual simulated pitch count — the one remaining `Date.now()`-seeded piece, and only for this cosmetic layer.

**Not real yet, a deliberate scope line**: the roster/player *generation* itself is unaffected by this — no new career-simulation or Growth-Model integration was added, this only swapped which rosters a one-off game draws from (synthetic → the real, already-built 50-team league).

### 6. Real roster construction — done
`realLeague.js` + `rosterSeed.js`: all 50 real teams have a full, real **26-man roster** (9 lineup + 5 rotation + 8 bullpen [4 named roles: Long/Middle/Setup/Closer, + 4 unnamed depth arms] + 4 bench), generated via `generateEstablishedPlayer()`. MLB1 vs. MLB2 quality bands are deliberately ~20 points apart (`ROSTER_QUALITY_BY_TIER`); bench/bullpen-depth players get a further `DEPTH_QUALITY_DISCOUNT` below their team's starters (a real downgrade, not a lateral move). A small free-agent pool also exists (`freeAgents`, `teamId: null`) but nothing consumes it yet. `getTeamRoster(teamId)` resolves a roster's id array into `{lineup, rotation, bullpen, bench}` — **`bullpen` is ordered `[Long, Middle, Setup, ...4 depth arms, Closer]`**, Closer deliberately kept last because `selectNextPitcher`'s save-situation logic treats the last array slot as the closer.

Historical note: this roster originally generated only 18 of 26 spots (8 reserved for a planned HS draft). That reservation was abandoned once the Injuries system needed real bench/bullpen depth to substitute into — see the Injuries section. The *original* broader intent (fill each org's entire minor-league pyramid, not just the MLB active roster) was never built and still isn't — no AAA/AA/A rosters exist anywhere.

### 7. Season/schedule loop — done
`engine/season.js` + `data/season.js`. Schedule generation groups teams by `(tier, leagueId)` — **no interleague regular season** (`league-structure.md`: Foundry only plays Foundry, Exchange only plays Exchange, until the Cup/Finals) — and builds ~150 games/team via repeated shuffled round-robin cycles (the exact pairing *algorithm* isn't specced anywhere, this is a placeholder; the 150-games target and no-interleague rule *are* specced). `simulateSeason()` runs every scheduled game through the real engine: DH-aware lineups (Foundry = no DH, that day's starter bats; Exchange = DH), 5-man rotation cycling, real win/loss standings, and injury persistence (below). `Standings.jsx` / `Schedule.jsx` / `TeamDetail.jsx` all read this real data now (as does every other page at this point — see sections 5, 19, 20, 21).

~~Not modeled: promotion/relegation *execution*~~ — **done, see section 21.** Still not modeled: playoffs, the Cup tournament, roster expansion, the draft, free agency, real calendar/dates (games are an ordered sequence, not tied to actual dates — `season-calendar.md`'s full preseason/blackout-weekend/All-Star/playoff sequencing is a separate, later step).

### 8. Injuries and injury substitutions — done
`engine/injuries.js` implements `injuries.md`'s risk formula: `base_rate × position_multiplier × age_multiplier × durability_modifier × fatigue_multiplier[pitchers only]` (the fatigue term reuses `pitcherFatigue.js`'s existing `computeFatiguePenalty()` rather than reinventing pitcher tiredness). This is `durability`'s **first real mechanical use** anywhere in the codebase.

Severity tiers (`DAY_TO_DAY` / `SHORT_TERM_IL` / `LONG_TERM_IL` / `SEASON_ENDING` / `CAREER_ENDING`) carry **hard floors** — `gamesRemaining` never reaches zero before the real-IL-rule minimum elapses (10-day/60-day equivalents), regardless of how "healed" a player narratively is. A setback mechanic layers real recovery variance on top (a short-term injury can escalate to a more severe tier) — **bounded to a short window right after diagnosis/escalation, not a flat ongoing per-game hazard**, because a flat hazard compounds catastrophically with a long tier's duration (see Calibration notes — this was a real bug, caught and fixed).

In-game, only the **current batter** (after his PA resolves) and the **current pitcher** (after each pitch) roll for injury — not the other 7 fielders or non-batting baserunners, since this engine has no fielding-event or baserunning-event attribution to hook a risk into. On a hit, it forces a real substitution (pitcher side reuses the already-unconditional `selectNextPitcher`; hitter side uses new `selectEmergency*` variants in `hitterChanges.js` — same eligibility logic as the tactical selectors, minus the "must be a clear upgrade" quality gate). If nobody's available, the player continues — the same graceful-degradation fallback the engine already uses everywhere else a substitution pool runs dry.

`engine/season.js` persists injuries across games via `injuryStatusById` (same external-Map ownership pattern as `standingsById`) and filters injured players out of each game's roster (promoting an available bench player into the slot). `TeamDetail.jsx` shows `IL · Ng` / `OUT` tags on injured players; `BoxScore.jsx` shows `Injury: X for Y` substitution notes. Validated via `npm run validate:injuries`.

**Explicitly flagged, real future work — not generic background noise, specifically asked to be remembered**:
- **Fielding injuries** — needs a real fielding-event mechanic first (doesn't exist; defense currently has zero effect on outcomes at all).
- **"Playing hurt"** — every triggered injury is an immediate full substitution today; there's no "grits through a nagging injury at reduced performance" state. `consistency.js`'s `withPerformanceModifiers()` is the natural primitive to reuse once this is built.

Also deferred: cascading minor-league call-ups (blocked on the unbuilt Minor League System), the full AAA/AA/A organizational depth chart, real calendar-date-based healing that survives season boundaries (blocked on the still-nonexistent calendar model — durations are tracked in games missed, not real dates), catcher-specific injury-type severity profiles, CBA-negotiable IL duration.

### 9. Position-player fatigue — done
`engine/positionPlayerFatigue.js` implements `injuries.md`'s "Position Player Fatigue" section — a deliberately much lighter-touch companion to pitcher fatigue: `computeFatiguePenalty(consecutiveGamesPlayed)` (0 until a 6-game rest threshold, then climbs, capped at 5 — vs. pitcher fatigue's 28-point cap) and `computeFatigueRiskMultiplier(...)` (feeds into `injuries.js`'s `computeInjuryRisk` as the non-pitcher `fatigue_multiplier` term, scaled smaller than the pitcher version too). `applyFatigue()` nudges every on-field physical attribute (`HITTING_ATTRIBUTES`+`BASERUNNING_ATTRIBUTES`+`DEFENSE_ATTRIBUTES`) down by a flat amount — deliberately *not* an independent per-attribute roll like `consistency.js`'s form modifier, since this is a workload penalty, not a talent-consistency swing.

Cross-game tracking is owned by `engine/season.js`'s `consecutiveGamesPlayedById` Map (same ownership pattern as `injuryStatusById`) via `advanceFatigueForTeam()`, called once per side after each simulated game: a player who started gets his counter incremented, anyone who didn't (benched, hurt, rested — see below — or, for a Foundry no-DH team, the nominal DH-slot roster player, who doesn't actually play that game at all) gets reset to 0. `TeamDetail.jsx` shows a `Fatigued · Ng` tag (distinct color from the `IL` tag) next to affected position players — pitchers are never tracked by this mechanic at all (their own heavier fatigue system + the 5-day rotation cycle already serve as rest). Validated via `npm run validate:fatigue`.

**Auto-rest (added once the Manager entity existed, see section 16)**: `positionPlayerFatigue.js`'s `computeRestProbability(consecutiveGamesPlayed, analyticsVsFeel)`/`rollRest(...)` let a manager proactively bench a fatigued player before a game, driven by the **Analytics vs. Feel** slider — the doc's "data-driven models vs. gut instinct" framing maps directly onto the real-world load-management archetype (an Analytics manager proactively rests regulars; a Feel manager just keeps running them out). Reuses `computeFatiguePenalty`/`MAX_FATIGUE_PENALTY` (now exported) as the fatigue-severity fraction rather than a second "games over" constant. **Zero at/below a neutral (50) slider value** — deliberately asymmetric unlike the other five sliders, since there's no *prior* auto-rest behavior to preserve at neutral (nothing ever auto-rested before this); only `analyticsVsFeel > 50` starts proactively managing workload, so every caller without a real manager (every validate script, the standalone demo) sees zero behavior change. `engine/season.js`'s `resolveRestedRoster(roster, consecutiveGamesPlayedById, managerProfile, rng)` is a structural twin of the existing `resolveAvailableRoster` — applied *after* it in `simulateSeason`'s per-game loop (injuries are mandatory, rest is a voluntary managerial choice layered on top), same "first unused bench player in array order" simplification `resolveAvailableRoster` already uses (no position-eligibility check there either). `advanceFatigueForTeam`'s existing "not in playedIds → reset to 0" logic needed zero changes — a rested player already flows through the exact same code path as a benched/injured player. Confirmed live: a real team under a manager with `analyticsVsFeel` just barely above neutral (51/100) already shows meaningfully lower fatigue counts across its whole roster than before this change (previously several `Fatigued · 154g` maxed-out tags were common; now none). Validated via `validate:fatigue`'s extended sections 5-7, including a real-season comparison (an Analytics-leaning manager's regulars topped out at 9 consecutive starts vs. a neutral team's 154 — the cap-plateau problem this was built to fix, closed).

### 10. Hot/Cold Streaks — done
`engine/hotColdStreaks.js` implements `player-attributes-and-development.md`'s "Hot/Cold Streaks" section — purely descriptive, does **not** feed back into performance (respected by `plateAppearance.js`'s own header comment). Built as the first step toward the full Manager entity (see "Path to Managers" below): `Player.js`'s `streakState` field and `constants.js`'s `HOT_COLD_TIERS`/`HOT_COLD_THRESHOLDS` (±0.75/±2.0 SD five-tier table) already existed but were never computed anywhere until now.

The metric generalizes the doc's own worked example (a .250 hitter's expected 5-for-20, binomial SD ≈1.94) from a flat batting-average rate to a weighted, wOBA-like composite (`WOBA_WEIGHTS`, real-MLB-anchored linear weights): a batter's context-neutral baseline mean/variance is computed via `plateAppearance.js`'s extracted `computeOutcomeProbabilities(batter, pitcher)` (a pure refactor — `resolvePlateAppearance()` now just rolls against that same distribution) against a synthetic `LEAGUE_AVERAGE_PITCHER`, not his actual opponents — matching how real rate-stat projections are contextualized.

**Window shape — an exponentially-decaying (EWMA) accumulator, not a fixed game count.** A flat, uncapped cumulative sum was tried first and rejected: once a real hot stretch accumulates a large excess, a flat sum barely forgets it, requiring an unrealistic pile of contrary evidence (~1,000+ PA) to revert — nowhere close to "cool off within a month or so." `updateStreakState()` instead tracks a decaying `{effectivePa, effectiveTotal}` pair (`EWMA_DECAY_PER_GAME = 0.92`, half-life ≈8-9 games): a real ongoing streak keeps reading as a streak for as long as it's actually sustained (no fixed cutoff), while a genuine reversal fades back to Neutral within a believable few-week span. Below `MIN_STREAK_SAMPLE_PA` (16) effective PA, a reading is unconfirmed — `tier` reports `NEUTRAL` regardless of how extreme the raw SD looks, so a two-game burst (e.g. 4-for-4 then 1-for-4) never counts as a real streak.

Cross-game tracking is owned by `engine/season.js`'s `streakAccumulatorById` (internal, decaying accumulator per player) and `streakStateById` (the latest computed reading, returned from `simulateSeason()`) — same external-Map ownership pattern as the other cross-game accumulators. `TeamDetail.jsx` shows a `Cold`/`Ice Cold`/`Hot`/`On Fire` tag (gold for Hot/On Fire, blue for Cold/Ice Cold) **only for a confirmed streak** — the gating above means a one-game blip never surfaces a tag. Validated via `npm run validate:streaks`.

### 11. Platoon/handedness splits — done
`Player.js`'s `bats`/`throws` fields — purely cosmetic until now — genuinely affect outcomes via `plateAppearance.js`'s `platoonShift(batter, pitcher)`. A rating-point-equivalent shift per handedness pairing (`plateAppearanceConstants.js`'s `PLATOON_SHIFTS`), added into the existing skill-diff calculations for strikeout/walk/home-run/BABIP (sign flips for strikeout specifically, since that diff is oriented pitcher-minus-batter, opposite of the other three — documented inline, guarded by `validate:sim`'s directional asserts). Deliberately asymmetric per real MLB data: LHB vs LHP is the single toughest pairing, a bigger penalty than RHB vs RHP — not just a flat same-hand/opposite-hand split. Switch-hitters always resolve to the side opposite the pitcher's throwing hand (`effectiveBattingSide()`), always taking the platoon advantage.

**New rated attribute — `platoonSkill`** (`MAKEUP_ATTRIBUTES`, 20-80 scale): individual players vary in how much the population-level shift applies to them. `scaleFactor = 1 - (platoonSkill - 50) * PLATOON_SKILL_SCALE_SENSITIVITY` — 1 (unchanged) at the population average, compressing toward 0 as it climbs (a flatter-split "matchup-proof" hitter), growing above 1 as it falls (a classic short-side platoon player), and — per an explicit user ask — crossing slightly negative only at the true tail of the scale (~80, already rare by this engine's population-scarcity design), a small genuine reverse-split. Being a normal rated attribute (not a fixed-by-birth constant) means it's generated, scouted, and developed period-over-period with **zero extra wiring** — `createPlayer()`/`playerGenerator.js`/`growthModel.js` all already treat `MAKEUP_ATTRIBUTES` generically.

A pitcher with no assigned `throws` (e.g. `hotColdStreaks.js`'s context-neutral `LEAGUE_AVERAGE_PITCHER` reference, which predates this feature) is treated as handedness-neutral — zero shift, not a crash or `NaN` — the semantically correct reading for a reference opponent that shouldn't carry a specific platoon edge either way.

**Real calibration wrinkle, worth remembering**: `createPlayer()` defaults `bats`/`throws` to `'R'`, so any synthetic fixture that doesn't explicitly randomize handedness is an implicit same-handed (worst-case) matchup. `validate-game-loop.mjs`'s 500-game aggregate hit exactly this — its fixtures had always been implicitly all-same-handed (harmless before this feature existed), and once the platoon penalty was real, avg runs/game dropped from ~8.24 to ~6.71, a real regression, not an expected side effect. Fixed at the root cause: `makeBatter`/`makePitcher` there now assign handedness via the real generator's own `pickBats`/`pickThrows` (newly exported from `playerGenerator.js` for exactly this reuse) instead of leaving it defaulted, restoring ~8.28/8.53. **Lesson**: any synthetic engine fixture that doesn't explicitly set `bats`/`throws` is implicitly same-handed and will read as a systematically harder matchup than a realistic mixed-handedness roster — reuse `pickBats`/`pickThrows` rather than leaving handedness at the default when building a new fixture meant to represent a realistic population.

Also fixed in the same pass: `engine/season.js`'s `advanceFatigueForTeam()` had a one-game lag — a player injured *during* a game still got his fatigue counter incremented for that same game, since the pre-game resolved roster couldn't know he'd get hurt mid-game. Now also checks `injuryStatusById` (already updated with this game's injuries by the time fatigue advances) and force-resets immediately rather than waiting a game. Pre-existing edge case, not caused by platoon splits — just surfaced by the new RNG-driven outcome sequence exercising it for the first time.

Validated via the extended `npm run validate:sim` — new platoon-pairing rows, directional/magnitude/switch-hitter asserts, a population-weighted-average anchor check (using the generator's real `pickBats`/`pickThrows` proportions), and `platoonSkill` scaling asserts (compress/exaggerate/rare-flip). No lineup-construction or pinch-hit decision layer was built — this unlocks the *mechanic* the future Platoon Tendency manager slider will act on, not the manager decision itself.

### 12. Stolen bases — done
`engine/stolenBases.js` — nothing about stealing existed before this: no attempt decision, no success resolution, no box-score fields. Not specced in any design doc (only `managers.md` mentions a future Steal Aggressiveness manager slider); this engine's own placeholder logic, same status as `pitchingChanges.js`/`hitterChanges.js`'s own un-specced substitution decisions.

**Scope, confirmed with the user**: only 1st→2nd and 2nd→3rd (steals of home deferred — rare, situational, mostly suicide-squeeze territory in reality). Because a runner can only attempt when the very next base is open, `identifyStealOpportunity(bases)` finds **at most one** opportunity per plate appearance — real double steals (multiple runners breaking simultaneously) aren't modeled; a runner on first is simply blocked if second is occupied, but the runner on second in that same state still has his own independent shot at third if it's open.

`computeStealAttemptProbability(runner, situation, scoreMargin)` — a runner's own Speed/Baserunning-Instincts composite (reusing `hitterChanges.js`'s `speedComposite()`, now exported, the same "runner quality" concept already used for pinch-run decisions) shifts a per-situation base rate; zero outright once `|scoreMargin|` exceeds a threshold (not worth the risk in a blowout either way). **Deliberately has no innings-from-end gate** unlike the three `hitterChanges.js` substitution mechanics — stealing is a general in-game tactic, not an endgame-specific one.

`computeStealSuccessRate(runner, catcher, pitcher, situation)` — runner composite vs. the catcher's Arm Strength/Accuracy composite (their **first real gameplay mechanical use** anywhere — previously only fed `positionReassignment.js`'s fit-scoring weights), plus a smaller pitcher `control` term as a rough stand-in for "hold time/quickness to the plate" (an explicit user choice — no dedicated attribute exists for this, and control was judged a reasonable existing proxy over inventing a new one). `FIRST_TO_SECOND` and `SECOND_TO_THIRD` have distinct baseline attempt/success rates (illustrative placeholders, matching this project's tuning-status tone) — 2nd→3rd is rarer-attempted and a bit riskier.

**Wired into `game.js`'s per-half-inning loop**: `maybeAttemptSteal()` runs **before** `nextBatter(offense)` — critical ordering, since `nextBatter` mutates `offense.battingIndex` as a side effect. A caught-stealing increments `pitcherLine.outsRecorded` (a real out, affects fatigue/TTOP) but deliberately **not** `battersFaced` (the same batter is still up). If a caught-stealing is the 3rd out, the existing `while (outs < 3)` loop naturally handles it correctly — **the batter at the plate never gets a PA that half-inning**, matching real baseball (he leads off next inning). Exported for direct testability (matches `season.js`'s `resolveAvailableRoster` precedent) since this correctness property was judged important enough to unit-test in isolation rather than only trust by inspection.

`boxScore.js` gained `sb`/`cs` battingLine fields + `recordStolenBaseAttempt()`; `BoxScore.jsx`'s `BattingTable` gained SB/CS columns (same tabular treatment as the existing 2B/3B/HR/BB/K columns). Validated via `npm run validate:steals` — attempt/success direction, situation-baseline differences, the mid-PA-ending-inning correctness property (unit-tested directly against `maybeAttemptSteal` with a fixed-sequence fake `rng`), `outsRecorded`/`battersFaced` correctness, and a real-season wiring check (~0.5 SB/team/game in a 100-game smoke test). Confirmed live: SB renders correctly on `/box-score`.

### 13. Bunting / Small Ball — done
`engine/bunting.js` — nothing about bunting existed before this. Not specced in any design doc (only `managers.md`'s Small-Ball Tendency slider mention); this engine's own placeholder logic, same status as `stolenBases.js`. **Scope, confirmed with the user**: includes the suicide/safety squeeze (bunting with a runner on 3rd to score him) as one higher-drama "runner unconditionally breaks" mode — no separate lower-risk safety-squeeze variant (no Manager entity exists yet to drive that finer distinction).

**Key architectural difference from stolen bases**: a bunt is an *alternative resolution of the same at-bat*, not an independent mid-PA event — so it reuses the exact same `recordPlateAppearance()` call site already in `game.js`'s loop. `maybeAttemptBunt()` returns either `null` (proceed with a normal `resolvePlateAppearance`/`resolveBaserunning` pair, unchanged) or a `resolveBaserunning`-shaped result (`outcome` forced to `PA_OUTCOMES.OUT`) — everything downstream (pitch count, injury checks, box-score recording, run-scoring) stays a single unconditional call site either way. No early-`break` needed (unlike stolen bases) since a bunt attempt *is* the batter's full turn.

**New rated attribute — `buntingSkill`** (`HITTING_ATTRIBUTES`, not `MAKEUP_ATTRIBUTES` like `platoonSkill`): bunting is a physical/technical bat-control skill, so it *should* get the same per-game form jitter and position-player-fatigue nudge contact/power/eye already get. `buntComposite(player)` blends `buntingSkill` (0.7) and `speed` (0.3) — real speed/bunting correlation, per the user's explicit ask, modeled at the formula level rather than correlating the two attributes' generation (a bigger, riskier change to `playerGenerator.js`'s uniform per-attribute sweep — a deliberate scoping choice, not an oversight).

`computeBuntAttemptProbability()` layers several real factors the user specifically asked to have reflected, on top of a per-situation base rate (`SQUEEZE` rarer than `PLAIN`): a Foundry (no-DH) bonus (this league's established small-ball identity), a larger batting-pitcher bonus (only ever fires in a Foundry game anyway, so it naturally stacks), and a late-game/runner-on-first-only/0-1-out "manufacture a run" bonus (matching `hitterChanges.js`'s existing innings-from-end convention). `computeBuntSuccessRate()` is `buntComposite`-driven only — no defensive factor (predates fielding/positioning below, which was still deferred at the time this shipped).

**New export in `baserunning.js`** — `resolveSacrificeBunt(bases, batter)` reuses the existing private `advanceOnHit(bases, batter, 1)` helper (handles bases-loaded force-in-a-run correctly already) and discards the batter's own placement — a clean reuse of an existing primitive rather than new advancement logic.

**Plumbing addition**: `dhRule` now rides along on each side object (`season.js`'s `buildGameSide()` → `game.js`'s `createSide()`, same pattern as `consecutiveGamesPlayedById`), defaulting to `true`/Exchange (no bonus) for callers that don't know/care, like the standalone `/box-score` demo.

`boxScore.js` gained `sh` + extended `recordPlateAppearance()` (sacrifice credit only on success, matching real MLB rules — a failed attempt is a normal recorded AB/out); `BoxScore.jsx` gained an SH column. Validated via `npm run validate:bunt` — situation classification, attempt/success direction, the Foundry/batting-pitcher/manufacture-a-run bonuses, and forced success/failure on both `PLAIN` and `SQUEEZE` (including the critical double-out risk: a failed squeeze costs both the batter *and* the runner from third, unlike a failed plain sacrifice). Confirmed live on `/box-score`.

### 14. Fielding / Positioning (Defensive Management) — done
The biggest gap closed this session: **defense had zero mechanical effect on any outcome since the very first session** (`plateAppearance.js`/`baserunning.js`'s own long-standing header notes). `engine/fielding.js` — not specced in any design doc (only `managers.md`'s Defensive Management slider mention). This is Fielding/Arm Strength/Arm Accuracy's **first real effect on any outcome anywhere** — previously they only fed `positionReassignment.js`'s fit-scoring weights.

**Also fixed, a separate pre-existing gap found during investigation**: a runner on third **never scored on a groundout**, ever, regardless of positioning — `baserunning.js`'s groundball branch only ever handled the runner-on-first case. Confirmed with the user to fix this too (it's the prerequisite for modeling "infield in" at all).

`computeTeamDefenseComposite(defense)` averages Fielding (0.6)/Arm Strength (0.2)/Arm Accuracy (0.2) across the 8 real fielders currently on the field (excludes `DH` and the pitcher). Wired into `plateAppearance.js`'s `computeOutcomeProbabilities`/`resolvePlateAppearance` via a new optional 3rd param `{composite, noDoublesActive}` (safe defaults preserve every existing caller — `hotColdStreaks.js`'s baseline, `statLine.js`'s isolated matchup simulator — unchanged) — **BABIP/hit-split only**, deliberately; defense doesn't affect strikeouts, walks, or home runs in reality either.

**Three situational positioning tactics**, matching the slider's own description:
- **No-doubles** (`isNoDoublesActive` — defense leading, last 2 innings) shifts hit-type split toward singles, away from doubles/triples.
- **Double-play depth** turned out to be a direct extension of `baserunning.js`'s *existing* `rollDoublePlayChance` formula (which previously only read batter speed) — not a new decision layer at all, just a `defenseComposite` term added to it.
- **Infield-in** (`isInfieldInActive` — defense tied or down modestly, last 2 innings) is layered onto the newly-fixed groundout-scoring logic: on a successful throw home, the runner from third is out at the plate instead and the *batter* reaches first safely (the real trade-off, a different out at the cost of a new baserunner) — on failure, same as the routine case (run scores, batter out at first).

**Errors**: a ball that would otherwise be `PA_OUTCOMES.OUT` can instead become a fielding error (`computeErrorChance`, worse defense commits more), checked in `game.js` *before* `resolveBaserunning` runs (an error preempts whatever groundball/flyball/DP/infield-in sub-resolution that out would have gone through). New `baserunning.js` export `resolveReachedOnError` reuses `advanceOnHit(bases, batter, 1)` directly — unlike `resolveSacrificeBunt`, the batter *does* reach base this time, no override. Team-level `side.errors` counter (no per-player attribution — this engine has no specific-fielder-per-play resolution to support that). **Simplified same-play-only unearned-run rule**: no RBI and no earned run credited when a run scores on the same play as an error (a real MLB scoring convention); a runner who reached on an *earlier* error but scores later via a separate clean play is still counted earned in this v1 model — an explicit, flagged simplification short of full inning-reconstruction logic.

**Real bug caught by the validation script, not glossed over**: the first `rollDoublePlayChance` extension had `defenseComposite`'s term *subtracted* (copy-pasted the batter-speed term's sign without flipping it) — good defense was actually turning *fewer* double plays. `validate:fielding`'s directional assert caught it immediately; fixed to add the term instead.

`BoxScore.jsx`'s `LineScore` gained an E column next to the existing R column. Validated via `npm run validate:fielding` (11 sections — the most thorough script this session, matching the biggest blast radius: core PA engine *and* core baserunning touched simultaneously) — composite/BABIP/error/no-doubles/infield-in/DP-chance direction, all four situational trigger conditions, the groundout-scoring fix directly, `resolveReachedOnError`, `recordPlateAppearance`'s `isError` handling, and real-season wiring. Re-ran the full regression suite afterward — `validate:game`'s runs/game actually moved *up* toward the ~8.6-9.0 target (previously suppressed by the missing groundout-scoring case, now fixed) rather than down like the last two additions — a good sign the fix was a real, overdue correction, not just added noise. Confirmed live on `/box-score`: E column renders correctly.

### 15. Origin/Nationality/Retirement (cosmetic-only pass) — done
`managers.md` needs two things from `Player` before manager generation can reuse them: a nationality tag system ("ex-player managers draw nationality directly from their existing player record") and player retirement to exist at all ("an ex-player manager has to have stopped playing first"). Both were designed-but-unbuilt: `Player.js` already had `birthNation`/`heritageNation` fields, but every generated player was hardcoded `birthNation: 'USA'`, `heritageNation: null`; retirement didn't exist anywhere (no field, no function, no removal logic).

**Nationality** (`international-tournament-and-nationality.md`'s "shallow data, rich mechanic" design): new `models/generation/nationalityPools.js` — `BIRTH_NATION_POOL` (weighted, ~70% USA / ~30% foreign-born, illustrative placeholder matching real MLB demographic proportions) and `HERITAGE_NATION_POOL` (the birth pool plus several heritage-only nations) feed `pickBirthNation`/`pickHeritageNations`, wired into both `generatePlayer()` and `generateEstablishedPlayer()`. `heritageNations` (renamed from the unused singular `heritageNation`) holds 0-2 entries per `HERITAGE_NATION_COUNT_WEIGHTS` (78/18/4%, matching the doc's 75-80/15-20/2-5% split). **Explicit scope-down from the doc**: no regional weighting (e.g. "Miami-born skews Cuban") — no birth-region/city data exists on `Player` to drive that correlation, so heritage is drawn independently of birth nation instead. Also explicitly deferred: localized name pools by nationality (`namePools.js` stays USA-only regardless of `birthNation`). `TeamDetail.jsx` gained a `NationalityTag`, parallel to `InjuryTag`/`FatigueTag`/`StreakTag` — deliberately quiet: a plain-USA-no-heritage player (the common case) shows nothing, anyone with a non-USA birth nation or any heritage tag gets a small code (e.g. `DOM`, `VEN`) with full detail on hover.

**Retirement** (`engine/retirement.js`, new): `managers.md` originally sketched a bare age/decline soft-probability default. **Real user feedback reshaped this significantly** — retirement should be rare mid-season and mostly an end-of-season decision, and a season's injury outcome should be a real input, not just age/decline. Three triggers, evaluated together in one end-of-season roll per player:
1. Age/decline voluntary retirement — soft probability curve (0 below 32, rising through the high-30s/40s, no hard cutoff, matching Writers Corps'/Scouts'/Managers' own soft-retirement shape). Above age 33, a decline term adds further probability, approximating "decline below career peak" via current-vs-true-potential (no real peak-tracking field exists on `Player` — an explicitly flagged approximation, since a bust who never developed reads similarly to a declined veteran under this proxy).
2. Injury-driven, reusing `injuries.js`'s existing `INJURY_SEVERITIES` rather than inventing new state: `CAREER_ENDING` forces retirement outright (probability 1); `SEASON_ENDING` adds a real probability bump, but **only** for a player already at/past the same age-33 gate — "an older player who maybe planned to retire at season's end gets a season-ending injury and just calls it there," deliberately not applied to a young player with the same injury (he's expected back).
3. DFA'd-and-not-picked-up — **explicitly deferred, not built**, per direct user instruction to leave it for a future master roster-transaction system rather than a loose proxy now. No DFA/waiver/roster-transaction mechanic exists anywhere in this codebase (no trades, no waivers, no roster moves at all). Documented as a specific, named extension point in `engine/retirement.js`'s own header comment — the same "computed hook, not yet acted on" pattern already used for `reassignmentReaction.js`'s `requestsTrade`/`benchWorthy` flags.

`advanceCareerForRoster(roster, rng, {asOfDate, injuryStatusById})` rolls retirement across `lineup`/`rotation`/`bullpen`/`bench`, returns `{roster, retiredPlayerIds}` with retirees filtered out — same shape/precedent as `season.js`'s `resolveAvailableRoster()`, non-mutating like `growthModel.js`.

**Real constraint surfaced and accepted, not routed around**: this app has no season-to-season progression loop at all — `season.js`'s `simulateSeason()` plays one fixed schedule once, and `growthModel.js`/`development.js` (period-over-period aging) are themselves never called from that loop either, despite being fully built and validated. Retirement follows the exact same precedent: `advanceCareerForRoster` is real, tested, and ready for a future season-advancement driver to call at a season boundary, but isn't wired into `simulateSeason()` this pass (there's no boundary to hook it to, and the mechanic is meant to fire there, not mid-game anyway). No `RetiredTag` was added to `TeamDetail.jsx` for the same reason — nothing in today's live singleton roster data will ever actually retire.

Validated via `npm run validate:origin` (`scripts/validate-origin-and-retirement.mjs`) — nationality distribution/dedup checks, retirement probability direction (age, decline term, both age-gated), `CAREER_ENDING` forcing probability to exactly 1, a young player's `SEASON_ENDING` injury NOT bumping his probability, `rollRetirement`/`advanceCareerForRoster` correctness. All checks passed first run. Re-ran the full regression suite (touches `Player.js`'s schema and every generated player's `birthNation`) — all pass, no script asserted on the old `birthNation`/`heritageNation` shape. Confirmed live on `/teams/:id`: non-USA players show a nation code, USA-born players with heritage tags show `USA` with heritage detail on hover, plain-USA players show nothing.

### 16. Manager Entity — done (final "Path to Managers" step)
`managers.md` (v0.4) assembled in full: schema, generation, per-team assignment, and every one of the seven sliders wired into a real decision — the final item on the roadmap below.

**Schema/generation**: `models/Manager.js` (`createManager`) + `models/generation/managerGenerator.js` (`generateManager`) — a separate `MANAGER_ATTRIBUTE_SCALE` (1-100, `models/constants.js`) from players' 20-80 `RATING_SCALE`, since the doc explicitly tags the sliders "(1-100)". `MANAGER_SLIDER_NAMES` holds the seven; Temperament and Streak Read share the same scale for simplicity (the doc gives them no distinct one). **Origin** (`MANAGER_ORIGINS.EX_PLAYER`/`OUTSIDER`, ~75/25 placeholder split per the doc's own "needs a real number" flag) reuses `nationalityPools.js` directly for both types — an explicit simplification: no real pool of past players exists to draw an ex-player's record from, since this app still has no season-to-season loop (`engine/retirement.js`'s player retirement never actually fires in production either — see section 15). `formerPosition` is a cosmetic-only nod for ex-player managers, not a linked `Player` id. **League-flavor mean shift** (the doc's "nice natural tie-in, not a hard rule"): Foundry managers skew small-ball/quick-hook/Feel, Exchange skews platoon-heavy/patient/Analytics, applied as a gaussian mean shift at generation, not a hard constraint — confirmed live (Boston/Foundry: Small-Ball 75, Pitcher Hook 34 vs. New York/Exchange: Small-Ball 63, Pitcher Hook 80).

**Temperament & Streak Read fallibility** — new `engine/managerBehavior.js`, two independent "noise inversely related to a trait" mechanisms:
- `resolveGameManagerState(manager, rng)` implements the doc's `effective_slider_value = base + noise(Temperament)` — rolled **once per game per slider**, not per decision (the doc's "a manager could have an uncharacteristic night" framing means one roll, matching the engine's existing per-game jitter precedent). High Temperament → tight noise; low → wide.
- `perceiveStreakTier(actualTier, streakRead, rng)` — models a Feel-leaning manager's Streak Read fallibility by treating the five `HOT_COLD_TIERS` as an ordinal scale and adding noise inversely scaled to `streakRead`, covering both failure modes the doc names ("benching someone in a slump too late" and "riding a player who was never really hot") with one mechanism.

**Five sliders map onto existing fixed constants**, same "the constant becomes a neutral default, the slider shifts it" pattern every time (every new param defaults to 50 — the pre-Manager-entity fixed behavior exactly, so no existing caller/validate script needed to change):
- **Pitcher Hook** → `pitchingChanges.js`'s `shouldPullPitcher` (`FATIGUE_PULL_PENALTY_THRESHOLD` shifts).
- **Bullpen Usage** → `pitchingChanges.js`'s `selectNextPitcher` (`SAVE_SITUATION_MAX_LEAD` widens/narrows). These two sliders overlap enough in English ("long leash" vs. "let starters go deep") that the file now has an explicit comment splitting them: Pitcher Hook owns WHEN the current arm gets pulled, Bullpen Usage owns HOW liberally the best reliever gets deployed once you're in the pen.
- **Steal Aggressiveness** → `stolenBases.js`'s `computeStealAttemptProbability` (added straight to the base attempt rate — the cleanest 1:1 of the five).
- **Small-Ball Tendency** → `bunting.js`'s `computeBuntAttemptProbability`, same treatment.
- **Defensive Management** → `fielding.js`'s `isNoDoublesActive`/`isInfieldInActive` (`POSITIONING_INNINGS_FROM_END`/`INFIELD_IN_MAX_DEFICIT` widen with the slider — both signatures gained a new optional param).

**Platoon Tendency + Analytics-vs-Feel/Streak Read — real new decision logic, not just a parameterized threshold** (confirmed with the user first, since this was meaningfully larger scope than the other five): `hitterChanges.js`'s `selectPinchHitter` gained an optional manager-context param and a new `managerAdjustedOffensiveComposite` — both the incumbent and every bench candidate get scored with it instead of plain `offensiveComposite`, so the comparison stays fair on both sides. A **platoon bonus** reuses `plateAppearance.js`'s existing `platoonShift` (now exported) directly rather than reimplementing handedness-advantage math, weighted by Platoon Tendency. A **streak bonus** only applies when Analytics-vs-Feel is Feel-leaning (an Analytics manager ignores streak state entirely, per the doc) and runs the player's real Hot/Cold tier through `perceiveStreakTier` before applying it — a Feel-leaning manager with poor Streak Read can genuinely misjudge who's actually hot. Deliberately scoped to pinch-hitting only, not defensive replacement (Fielding-driven) or pinch-running (Speed-driven) — matches the doc's own "lineup and platoon decisions" framing.

**Manager Career Lifecycle — retirement only in this phase**: `engine/retirement.js` gained `computeManagerRetirementProbability`/`rollManagerRetirement` — a much simpler, older-tuned age curve than player retirement (0 below 55, rising through the 60s-70s; no decline/injury terms, since managers don't have eroding ratings or get injured in this sim). At the time this phase shipped, this was standalone and unwired, same status as player retirement — no season-to-season loop existed yet to call it from. **Firing and Rehiring were built in a later phase** (section 17 below) — unlike retirement, they turned out not to need a season-to-season loop at all. **Hall of Fame eligibility was also built in a later phase** (section 18 — it's what finally built the season-to-season loop this retirement mechanic needed). **WBC National Team Managers remain explicitly NOT built**, blocked on a specific, named missing prerequisite (see "what's not built yet" below) — not a vague "roster stuff, later" deferral.

**Team assignment**: new `models/seed/managerSeed.js` (`buildSeedManagers`) generates exactly one manager per team (50 total, an inferred 1:1 cardinality the doc never states outright but its rehiring language implies). `data/realLeague.js` gained `managers`/`managersById`/`getTeamManager`, same shape as the existing player triple.

**Wired into the game loop**, following `dhRule`'s exact "rides along on the side object" precedent: `season.js`'s `simulateSeason` gained an optional `getTeamManager` param (defaults to `() => null`, so every existing caller is unaffected); `buildGameSide`/`game.js`'s `createSide` thread `managerProfile` (default: a neutral, all-50s synthetic manager) and `streakStateById` through, and `createSide` computes `managerGameState` (the per-game Temperament-noised effective slider values) once via `resolveGameManagerState`. **UI**: `TeamDetail.jsx` gained a `ManagerCard` — name, Origin badge, age, `NationalityTag` (reused directly, since a Manager and a Player share the same `birthNation`/`heritageNations` field names), and all nine numeric attributes in a labeled grid.

Validated via `npm run validate:managers` (`scripts/validate-manager-entity.mjs`, 13 sections) — generation shape/origin-split/league-flavor direction, Temperament noise spread direction, all five clean sliders' directional effect, the platoon-aware and streak-aware pinch-hit logic (including `perceiveStreakTier`'s accuracy-vs-Streak-Read direction), manager retirement, and a real simulated season with real managers attached producing no NaN/crashes. **All checks passed on the first real run** — no bugs caught this time, unlike Fielding's DP-sign-bug or Streaks' flat-sum redesign. ### 17. Manager Firing & Rehiring — done
`managers.md`'s Career Lifecycle ties Firing to "the main design doc's existing 'Coaches fired' Scripted Event category (triggered by win%, chemistry, owner patience)." That entry (`baseball-sim-design-doc.md`) turned out to be the *entire* spec — three named factors, zero numeric thresholds, no generic Scripted Event framework ever built (only disconnected mock flavor data existed). Of the three factors: **win%** was real but not exposed as a reusable helper; **owner patience** had zero elaboration anywhere in the docs; **chemistry** has a genuine future design in `player-relationships.md` ("computed as an aggregate... of the current roster's individual Org Affinity scores"), itself unbuilt. Built the trigger from **win% + a new, honestly-flagged owner-patience stat** — chemistry stays explicitly deferred with its real, named blocker, not faked or glossed over.

**A good realization during design**: unlike player/manager retirement (which need a season-*to*-season boundary that doesn't exist), firing is naturally an *in-season* event — `mockData.js`'s own old flavor text already assumed this ("Manager dismissed after 14-32 stretch"). This is wired directly into `engine/season.js`'s existing single-season loop, not left standalone-and-unwired like the two retirement mechanics.

`engine/managerFiring.js` (new): `computeWinPct(wins, losses)`; `updateOwnerPatience(currentPatience, won)` — a bounded 0-100 random walk, asymmetric on purpose (a loss drains it faster than a win restores it — "owners get impatient faster than grateful"); `computeFiringProbability(winPct, gamesUnderManager, ownerPatience)` — 0 below a minimum sample (`MIN_GAMES_BEFORE_FIRING_ELIGIBLE`, 20 games *under the current manager*) and 0 at/above .500 (no team fires a .500-or-better skipper under this model); patience *amplifies* the win%-driven probability rather than acting independently (a bad record under a patient owner is safer than the same record under an impatient one).

**Tenure, not season-to-date**: `season.js` gained `tenureRecordById` (wins/losses under the *current* manager, reset on every hire) — deliberately not the team's whole-season `standingsById` record, so a new hire gets a genuinely clean evaluation window instead of inheriting his predecessor's bad record and risking an almost-immediate re-firing.

**The real "career ladder" the doc wants**: `availableManagerPool` (starts empty) — a fired manager is pushed there (excluded from immediately replacing himself, since the replacement pick happens before the push); a new hire pulls from the pool first, only generating a fresh manager when it's empty. `managerAssignmentById` (pre-seeded from `getTeamManager` at loop start) is the only thing every per-game manager lookup reads from then on, since assignments can change mid-loop; a `firings` log (`{gameNumber, teamId, firedManagerId, hiredManagerId, winPctAtFiring}`) records every event.

**Backward compatibility, same pattern as auto-rest**: the whole mechanic is gated on a team actually having a real manager assigned (`getTeamManager` returning non-null) — a team running on the neutral synthetic default (every existing validate script that doesn't pass `getTeamManager`) is never fired or hired, zero behavior change. Confirmed by re-running `validate:season` unchanged. Production (`data/season.js`) passes a real `getTeamManager` for all 50 teams, so Firing & Rehiring is fully live there — 25 real firings occurred league-wide over a full 150-game season in testing, and pool-reuse (a fired manager hired by a different club) is *deterministic*, not just probable, once 2+ firings happen anywhere in the league (the pool starts empty, so only the very first firing ever generates a fresh manager — every firing after that necessarily finds a non-empty pool).

`data/season.js` gained `getCurrentTeamManager(teamId)` (the season's final assignment, not the static seed one) and `getTeamManagerChanges(teamId)`; `TeamDetail.jsx`'s `ManagerCard` switched to the season-aware getter and gained a compact "Manager Changes" note when a team's manager changed in-season. Confirmed live: New York's `ManagerCard` correctly shows its new manager (hired from Camden, NJ) with "Fired after game 1504 (.481)" for the predecessor.

Validated via the extended `npm run validate:managers` (sections 14-18) — `computeWinPct`/`computeFiringProbability`/`updateOwnerPatience` direction and gating, the deterministic pool-reuse invariant, and real-season wiring. All checks passed first run. Re-ran the full 13-script suite — all pass, `validate:season` (no `getTeamManager` passed) completely unaffected.

### 18. Hall of Fame — done
`awards-and-hall-of-fame.md`'s Hall of Fame was the last named Manager-adjacent gap. It turned out to need four stacked prerequisites, not one: a real season-to-season progression loop (nothing had ever aged/developed/retired a roster across seasons — `simulateSeason()` only ever played one fixed schedule once), career-length stat accumulation (nothing had ever summed even a single season's stats before), a Hall-case-score formula for both batters/pitchers and managers (the doc itself defers this "until players actually exist and accumulate history"), and a Writers Corps electorate (didn't exist in any form). All four are now real and wired together; per an explicit user choice (asked via `AskUserQuestion`: build eligibility rules standalone, or the full prerequisite stack), this went with the full stack rather than a shallow standalone eligibility check.

**Season-total stat accumulation** (`engine/season.js`): `seasonBattingStatsById`/`seasonPitchingStatsById`, summed from each game's box-score lines plus W/L/S. `BATTING_STAT_FIELDS`/`PITCHING_STAT_FIELDS`/`emptySeasonBattingTotals`/`emptySeasonPitchingTotals`/`groupTeamsForScheduling` were promoted from module-private to exported for reuse by the files below.

**`engine/leagueProgression.js`** — the real season-to-season driver, composing three previously-real-but-never-called mechanics for the first time anywhere in this codebase: `growthModel.js`/`development.js` (growth + position reassignment + refusal reaction) and `engine/retirement.js` (player + manager retirement). `advanceOffseason` runs this once per team per season boundary; a retiree is replaced via `generateEstablishedPlayer`/`generateManager` at the team's tier quality band (an explicit simplification: doesn't distinguish the original slot's core-vs-depth discount, since `rosterSeed.js`'s `DEPTH_QUALITY_DISCOUNT` is module-private and inferring "was this a depth slot" from array position would be fragile). `simulateLeagueHistory(teams, rosterByTeamId, managerByTeamId, writers, {seasons, gamesPerSeason, onSeasonComplete}, rng)` loops `simulateSeason()` → folds career stats → `advanceOffseason()` → repeat, tracking pennants (best-record-per-group — an explicit flagged proxy for "championships," since no real playoff system exists) and calling the optional `onSeasonComplete` progress callback each season (used by the snapshot script below for visibility on a multi-minute run).

**Writers Corps** (the voting electorate): `models/Writer.js` (schema, parallel to `Manager.js`), `models/generation/writerGenerator.js` (`generateWriter` — reuses `namePools.js`'s US-only pool per the doc's own instruction, age 24-30 start), `models/seed/writersCorpsSeed.js` (`buildWritersCorps` — one-or-more writers per team's city, count scaling with `marketSize` via a project-placeholder formula since the doc itself punts on exact numbers), `engine/writerRetirement.js` (age-60-ish soft retirement curve, matching the doc's own "simpler, lower-stakes version" framing, same-city replacement wired into `simulateLeagueHistory`).

**`engine/hallOfFame.js`** — `isHallEligible` (the two LOCKED numbers, ported verbatim from real BBWAA rules: 10 years service, 5 years retired); `computeBatterHallCaseScore`/`computePitcherHallCaseScore`/`computeManagerHallCaseScore` (weighted counting-stat sums). Hits/home runs (batters) and wins (pitchers) are anchored to the doc's real scaled milestones (500 HR→~460, 3,000 hits→~2,775, 300 wins→~278, the exact 150/162 ratio); every other counting stat's "great career" denominator (RBI, runs, SB, strikeouts, saves, innings, and the entire manager formula) is this project's own unanchored placeholder, flagged separately in the file header. **Two real bugs caught and fixed while building `validate:hof`/the snapshot script**:
1. `validate:hof`'s section 5 forced retirement deterministically via a constant `rng = () => 0` — but `advanceOffseason` runs growth first, which calls `gaussianRandom(rng, ...)` internally, and `gaussianRandom` has `while (u === 0) u = rng()`, which spins forever against a true constant-zero rng. Fixed by using `() => 0.0001` instead. **A constant-zero rng is safe for a plain `rng() < probability` comparison but not safe as a general "force everything" rng anywhere `gaussianRandom` gets touched** (growth variance, scout-error rolls, Temperament/Streak-Read noise, etc.) — use a small nonzero constant there instead.
2. `seasonsPlayedById` was incrementing once per player per *stat source* (once for appearing in `seasonBattingStatsById`, again for `seasonPitchingStatsById`) rather than once per season — a Foundry (no-DH) pitcher, who both pitches and bats, was accumulating two seasons of "service" per real season played. Caught via a sanity print, not `validate:hof` itself (a real gap in that script's coverage — it checked accumulation and plausibility but never an explicit `seasonsPlayed <= totalSeasonsSimulated` upper bound, which would have caught this directly). Fixed by unioning both key-sets into one `Set` before incrementing.

**A real calibration bug, also caught by a dry run, not a formula-shape unit test (those can't catch a magnitude-scale mismatch against real simulated data)**: the snapshot script's first draft used a shortened 100-game season to save build time; a 20-season trial's best career topped out at case score 38.6, nowhere near `hallOfFame.js`'s 70-point vote-center — meaning zero candidates would ever get elected, no matter how good, because the case-score formula's milestone anchors are calibrated to real 150-game-season career pacing and a shortened season structurally can't produce milestone-scale counting stats. Fixed by switching to the real 150-game length (confirmed: a 10-team/15-season/150-game trial reached case score 93.1) — timing math confirmed this isn't meaningfully slower (~1279 games/sec, full run ~100s). **When a formula is anchored to real-world numbers, always sanity-check it against the actual data the engine produces before trusting the formula in isolation** — a shortened-for-speed simulation parameter can silently break the anchor's whole premise.

The last named blocker on "what's not built yet" — until now this app had zero shared React state anywhere, so it could never advance past one simulated season. `engine/leagueProgression.js`'s `advanceOffseason` (built for the Hall of Fame snapshot script, section 18) was real and validated but never wired into the live app. This wires it in: a real "Simulate Next Season" action, persisted across reloads (explicit user choice via `AskUserQuestion` — the simpler alternative, resetting to season 1 on every reload, was offered and declined).

**`data/season.js` completely repurposed** — from "eager static singleton" to "live, persisted, advanceable season state":
- **Rng, deliberately not one continuously-mutating instance**: `seasonRngForNumber(n) => createRng(SEASON_RNG_BASE_SEED + (n - 1))` derives a fresh, deterministic rng from the season number alone. `createRng`'s closure mutates its own internal state on every call — a single long-lived instance touched anywhere React might double-invoke (a lazy initializer, a `useReducer` reducer body — both of which React 18 StrictMode, active in `main.jsx`, deliberately double-invokes in dev to surface impure code) would silently desync from a StrictMode-free build. Deriving fresh per season sidesteps this entirely, and also means there's nothing rng-related to serialize for persistence. Season 1 reproduces this league's original single-season seed (20260201) exactly — confirmed by diffing against the pre-refactor static values directly (byte-identical standings for several teams).
- **Persistence**: `localStorage`, versioned key (`diamondLedger.leagueState.v1` — a future shape change just falls back to a fresh season 1 rather than crashing on old data). `saveState`/`loadState` wrap `JSON.stringify`/`parse` with try/catch (never let a full/blocked/absent — e.g. a Node script importing this module — `localStorage` crash the app) and a generic replacer/reviver pair for `Map`↔plain-object round-tripping plus the non-JSON-safe `Infinity` that genuinely occurs in `injuryStatusById.gamesRemaining` for season-/career-ending injuries (a naive `JSON.stringify` silently turns that into `null`, which would misread a permanently-out player as recovering after a reload).
- `export const initialLeagueState = loadState() ?? computeFreshSeason1State();` — computed **once at module load**, outside React entirely, immune to StrictMode's double-invocation.
- `export function advanceToNextSeason(state)` — pure: runs `advanceOffseason` then `simulateOneSeason` on the result, returns the new state. Doesn't touch storage itself (the caller does).
- `export function resetToSeason1()` — clears storage, returns a fresh season-1 state.

**`src/state/LeagueStateContext.jsx`** (new) — thin React wiring only. `useReducer((state, action) => action.payload, initialLeagueState)`: a trivial, side-effect-free "replace state" reducer, safe under StrictMode's double-invocation (same payload in, same result out; no rng or other side effect happens inside the reducer — all of that already ran inside `advanceSeason()`/`resetSeason()`, which are plain event-handler callbacks StrictMode does not double-invoke). `useState` for `isSimulating`, separate from the reducer. `advanceSeason()` defers the actual ~3-4s computation one tick via `setTimeout(fn, 0)` so the loading text has a chance to paint first — not spec-guaranteed, but the standard practical idiom for this, reliable enough in every real browser for a one-off progress affordance; a Web Worker would be the fully-correct fix but is disproportionate scope here. Exposes the same getter names/signatures `data/season.js`'s old static exports had (`getTeamRoster`, `getTeamRecord`, `getTeamResults`, `getPlayerInjuryStatus`, `getPlayerFatigueStatus`, `getPlayerFatiguePenalty`, `getPlayerStreakState`, `getCurrentTeamManager`, `getTeamManagerChanges`, `getLeagueWireEvents`, `buildMatchup` — renamed from `buildRealMatchup`) plus a memoized `playersById` rebuilt from the live `rosterByTeamId` (needed since a retiree is replaced by a brand-new player object/id over time — `realLeague.js`'s static `playersById` goes stale the moment a season advances).

**Consumer migration** — mechanical, same function names: `App.jsx` wraps `<Routes>` in `<LeagueStateProvider>`; `Standings.jsx`/`Schedule.jsx`/`TeamDetail.jsx`/`Overview.jsx`/`Events.jsx`/`BoxScore.jsx` swap their `data/season.js` import for `useLeagueState()`. **`TeamDetail.jsx` also switched its roster lookup from `realLeague.js`'s static `getTeamRoster` to the hook's live one** — the one non-mechanical, easy-to-miss change, since otherwise its roster display would silently freeze at season 1 forever even as seasons advance. `Overview.jsx` gained the primary "Simulate Next Season" control (season number, disabled-button + loading text while `isSimulating`) and a "Reset to Season 1" action (a natural companion to persistence — otherwise there'd be no way back to a fresh start without manually clearing browser storage). `Financials.jsx`/`Cup.jsx`/`HallOfFame.jsx` are unaffected — confirmed they only read `teams` (static identity data) or the frozen HOF snapshot.

### 24. Domestic (HS) Draft — done (Phase 2 of "Path to Draft, Minors & Free Agency")

### 25. College System — done (Phase 3 of "Path to Draft, Minors & Free Agency")
The single biggest gap in the amateur pathway: Phase 2 shipped with every drafted player signing immediately at a 100% placeholder rate. The user confirmed the **full pathway**, not a scoped-down version — a real, persistent, multi-year college population (school, class year, redshirt, draft rights), not just a modifier bolted onto the existing draft class.

**A real found asset**: `engine/growthModel.js`'s `advanceDevelopmentPeriod` already had a `locationModifier` parameter, explicitly reserved years of build-time ago "for the future college-prestige/specialty system" (its own header comment says so verbatim). This phase is its first real consumer — **zero changes needed to `growthModel.js` itself**.

**Three population-realism problems the user caught before implementation started, all addressed by design, not patched after the fact**:
1. **Season-1 cold start** — an empty college system would take 3+ real seasons to populate years 2-4 on its own. Fixed via `seedInitialCollegePopulation`, a one-time bootstrap (season 1 only) that backfills all 4 class years at once: each cohort is generated as a normal 17-18 HS senior, then has its birthdate shifted back and the corresponding number of real `advanceDevelopmentPeriod` college-year calls fast-forwarded, so age and developmental progress land consistently together.
2. **Unbounded aging free-agent pool** — nobody wants 1,000 29-year-olds sitting unsigned forever. Fixed with `rollFreeAgentRetirement`, a dedicated, steep age curve (`FREE_AGENT_RETIREMENT_AGE_CURVE`) reaching effective certainty by the late 20s — deliberately **not** `engine/retirement.js`'s established-pro curves, which don't fire until the 30s and don't fit a never-signed amateur washout's much younger decision to give up.
3. **Elite-player statistical inflation** — an ever-growing, never-pruned pool would eventually accumulate an implausible number of genuinely elite players by sample-size math alone, even with a small elite fraction per batch. Kept bounded by two things together: `resolveDraft`'s existing best-available-by-scoutedPotential selection (a genuinely elite player is essentially never passed over unless 500+ *better* players also exist in that exact year's pool) plus the retirement curve capping how large the backlog can ever get.

**NHL-style draft-and-follow, reconciled with the user's separately-specified refusal branch**: every draft selection first rolls a rare refusal chance (`DRAFT_REFUSAL_PROBABILITY`, an unattached free agent, not bound to any team) — distinct from the doc's main framing, where a team's rights persist through a drafted player's *entire* college career once established. A player who already has rights held from a prior season does **not** re-enter the draft pool at all (`rollClaimedPlayerDecision` — his own annual decision directly with his own team, no competition, no second refusal roll).

### 27. Season persistence migrated to IndexedDB — done (fixes the localStorage quota overflow from section 26)
`data/season.js`'s `saveState()`/`loadState()` had persisted the live league state to `localStorage` since section 20; by the time International Academy (section 26) shipped, the real serialized size (~21.5MB) was reliably exceeding `localStorage`'s typical ~5-10MB-per-origin quota, silently breaking cross-reload persistence (an explicitly-requested feature). Root cause was structural, not a one-off: College's and the International Academy's free-agent pools/enrollment maps are **retirement-bounded, not capped** — they're designed to keep growing every season at a large steady-state size, so `localStorage` could never keep up long-term. **New `data/indexedDbStorage.js`** — a small, purpose-built wrapper (no new npm dependency), one object store (`leagueState`), one key (`'current'` — no multi-slot save concept exists). **`data/season.js`**: `saveState`/`resetToSeason1` are now `async`; a new `loadStateAsync()` (exported) replaces the old synchronous `loadState()`. Because IndexedDB has no synchronous read API, `initialLeagueState` is now **always** `computeFreshSeason1State()` (deterministic, fixed-seed season 1 — unchanged reproducibility) — the real "was there a saved game" check moved out of eager module-load entirely.

**`state/LeagueStateContext.jsx`**: a new mount-only `useEffect` calls `loadStateAsync()` and dispatches a real save (if one exists) before the app ever renders — gated behind a new `isHydrating` state that shows a brief "Loading your league…" message instead of `{children}` while it resolves, so no page flashes fresh season-1 data that then jumps to a real save. `advanceSeason`/`resetSeason`'s existing `setTimeout` bodies became `async` to `await` the now-async `saveState`/`resetToSeason1`. Old localStorage entries are left alone, not migrated (matching this codebase's own every-version-bump precedent: "an old save is simply ignored... exactly what the versioning exists for") — a best-effort `localStorage.removeItem` in the hydration effect is pure hygiene, not data preservation.

### 31. The Cup Engine — Group Stage — done (Phase 3, Group Stage half, of "The Ledger Cup" build arc)
`in-season-tournament.md` (v0.6)'s real cross-tier group stage. Phase 1's own header flagged the real problem this phase had to solve and deliberately left unsolved: knockout rounds depend on the previous round's winners, and both the group stage and knockout need injuries/fatigue/hot-cold streaks to keep evolving continuously across regular-season AND Cup games, in true chronological order — not reset by a second, independent simulation pass. Given the size of this phase relative to every other phase in the project's history, it's scoped to **the Group Stage half only** — the Knockout Bracket + genuinely two-season-spanning bracket state is a deferred follow-up, Phase 3b (see the arc roadmap below), matching this project's own "one right-sized, fully-validated, fully-committed chunk per session" cadence.

**The core architectural prerequisite: `engine/season.js`'s `simulateSeason` split into two composable pieces.** It used to be one monolithic function — build every internal Map fresh, loop over the *entire* schedule once, return everything at the end — with no way to pause mid-season, run a different batch of games against the exact same live state, and resume. New `createSeasonState(teams, getTeamManager)` (today's local `const` declarations, lifted out unchanged) + `simulateGamesIntoState(seasonState, teams, getTeamRoster, games, rng, options)` (the old per-game loop body, now callable more than once against the same live state) replace it. `options` gates `trackStandings`/`trackManagerLifecycle`/`trackSeasonStats` (each defaulting `true`) and an overridable `rotationIndexById` — **injuries, fatigue, and hot/cold streaks are never gated**, since keeping those genuinely continuous is this whole extraction's reason to exist. `simulateSeason` itself becomes a thin wrapper (`createSeasonState` + one `simulateGamesIntoState` call over the full schedule, every option `true`) — byte-identical to its old behavior at a fixed seed, proved by a new `validate:season` section 9, same technique Phase 1's `validate:calendar` used for its own no-op regression. Every one of the ~15+ existing callers (every other validate script, `leagueProgression.js`'s offline Hall-of-Fame pipeline) is completely unaffected.

**New `engine/ledgerCup.js`** (one-concern-per-file, matching `promotionRelegation.js`/`playoffs.js`'s precedent):
- **`drawCupGroups(teams, quotientByTeamId, rng)`** — Champions-League-style pot draw into 10 groups of 5 (3 MLB1 + 2 MLB2), enforcing the doc's league-balance constraint (MLB1 slots: ≥1 Foundry + ≥1 Exchange; MLB2 slots: exactly 1 of each). **Two genuinely different algorithms for the two tiers, not one reused approach** — MLB1's looser "not all 3 same league" constraint uses 3 Quotient pots (top/mid/bottom 10 across both leagues) shuffled independently with a bounded validate-and-retry (small n=30, same "no fancy CS optimization" style as the anti-tanking elimination detector). MLB2's *strict* "exactly 1-1" constraint can't be satisfied reliably by a naive global top-10/bottom-10 quotient split (the math doesn't guarantee a valid pairing exists at all, depending on how many of each league land in each half) — built correct **by construction** instead: rank each league's 10 teams separately, split each into a top-5/bottom-5 pot, pair every top-half team with a bottom-half team from the OTHER league. Zero retries, zero chance of failure, still Quotient-informed.
- **Group-stage scheduling** reuses `engine/season.js`'s own `buildGroupSchedule(group, 12, rng)` directly — **a real bug caught during this session's own smoke-testing, not glossed over**: a 5-team group's round-robin "cycle" is a full round-robin over *every pair* (C(5,2) = 10 games), not `n-1` (4) — an initial implementation sliced weekends using the wrong chunk size (4 instead of 10), silently desyncing which games belonged to which weekend. **A second real bug caught during smoke-testing**: `buildMlb2GroupSlots`' first draft called `shuffle(...)` *inside* a `.map()` callback — re-shuffling per element instead of once per pot — which scrambled the index-based 1:1 pairing into duplicate/missing teams (a real draw came back with only 47 of 50 teams present, 3 teams silently doubled-up). Fixed by shuffling each pot exactly once, before the `.map`.

**The orchestrator — `simulateSeasonWithCup`** — composes `engine/calendar.js`'s `weekPlan` with the new state-splitting primitives: walks `weekPlan.weeks` in order; an OPEN week pulls that week's already-`.week`-tagged slice of the regular schedule and runs it with standings/manager-lifecycle/stats **on**; one of the 3 H2 BLACKOUT weeks (front-loaded, per `calendar.js`'s own precedent) runs that weekend's group-stage games (all 10 groups, 100 games) with those three tracked **off** but injuries/fatigue/streaks still fully live, using a **separate, local** Cup rotation-index Map — matching `engine/playoffs.js`'s own established precedent of a local, non-persistent tournament rotation counter. When `cupGroups` is `null` (no Quotient history yet), this degrades to running the exact same open-weeks-only path `simulateOneSeason` runs today — **confirmed byte-identical at a fixed seed** (`validate:cup` section 6).

**`data/season.js` wiring**: new `cupState` field, `{groupStagePhase: 'NONE'|'GROUP_STAGE', groups, cupGroupStandingsById, advancingTeamIds}` (renamed from a plain `phase` to `groupStagePhase` in Phase 3b once a sibling `knockout.phase` was added — see §32). Season 1 stays `NONE` (no Quotient history exists yet to seed pots from — computed only once season 1's own regular season + playoffs have run). Every season from season 2 onward unconditionally draws a real group stage from **the prior season's own final `quotientByTeamId`** (before that season's own decay step touches it) and folds the resulting Cup games into Quotient right after the regular-season fold, before playoffs. **`STATE_SCHEMA_VERSION` bumped 10 → 11** (further bumped to 12 in Phase 3b).

### 32. The Cup Engine — Knockout Bracket — done (Phase 3b, of "The Ledger Cup" build arc)

### 36. 50-man Roster System — Contracts & Salaries — done (Phase 3 of the "50-man Roster System" arc)
`Financials.jsx` used to say outright: "Payroll itself isn't shown yet — no salary/contract mechanic exists in the engine." This phase makes that sentence false — the first real dollar figures anywhere in this codebase (every other financial value, market size and owner wealth included, stays an abstract 0-1 scale). Confirmed with the user before implementation: **every org-affiliated player gets a real, individually-tracked contract** — not just the 50-man MLB pool, but every AAA/AA/A/Rookie affiliate player too, matching `financial-model-expenses.md`'s own "ties to... the AAA/AA/A minor league system" language. A large population (order of several thousand players across 50 orgs) but computationally cheap — a per-player formula, no simulation cost.

**A real constraint this phase runs into: no Service Time yet.** Real MLB salary structure is driven by service time (pre-arb minimum, arbitration years, free-agent value), but Service Time is Phase 4, still unbuilt. This phase uses an explicitly flagged **age-based proxy** (`computeServiceTimeProxyFraction`, ramping 0→1 from age 20→28) standing in for "has he accrued enough time to command full market value" — same status as `engine/retirement.js`'s own age/decline proxy standing in for a still-unbuilt Scouts system. Phase 4 is expected to replace this proxy with a real day-accrual signal.

**New `models/Contract.js`** — `CONTRACT_TYPES = {MAJORS, MINORS, BOTH}`, `createContract`. **`models/Player.js`** gained `contract: null` by default — a real `Contract` for anyone inside an organization's system, `null` for college/international amateurs (NIL, not team salary, per the doc) and unsigned free agents.

**New `engine/contracts.js` — deliberately pure, no rng anywhere.** A contract is an objective valuation of ability + experience, not a random roll — this also sidesteps a real threading problem: live, user-triggered signing actions (`engine/freeAgency.js`) have no seeded rng available the way season simulation does, so a pure formula means those call sites need zero rng plumbing. `generateMajorsStyleSalary` (quality via `playerQualityScore`, exponentially curved toward `MLB_MAX_SALARY`, scaled down toward `MLB_MIN_SALARY` by the service-time proxy) covers both MAJORS (active 26) and BOTH (Reserve/Taxi pool) contracts — a BOTH contract is simplified to the same formula as a real MLB deal, flagged, since a true split-contract distinction is Phase 5/7 territory. `generateMinorsSalary` (level base + a small quality bonus) covers everyone else. `generateContractForPlayer(player, context, level, asOfDate)` dispatches on context: `'ACTIVE'` → MAJORS/guaranteed, `'RESERVE_TAXI'` → BOTH/guaranteed, `'MINORS_DEPTH'` → MINORS/not guaranteed.

**`assignMissingContracts`** is the season-boundary backfill that makes this tractable without touching a dozen different player-creation call sites: it walks every team's active roster, Reserve pool (live-resolved via `eligiblePlayersForTeam`, already exported from `rosterProtection.js` for exactly this kind of reuse), and full AAA/AA/A/Rookie affiliate rosters; anyone with `contract: null` gets one generated via the right context, and **anyone who already has a contract is left completely untouched — salary is sticky once assigned.** Called once near the end of both `computeFreshSeason1State` and `advanceToNextSeason`, after that season's full draft/college/international/backfill churn has already produced every new player who needs one — a single call sweeps up everyone, with zero changes needed to `draft.js`/`college.js`/`internationalAcademy.js`/`minorLeagues.js`.

**A known, explicitly-flagged simplification**: a contract's `type` is assigned once and can go stale if a player is later promoted/optioned between levels (e.g., a pure-MINORS player promoted straight to the active roster via `promoteAndBackfill` would still show `MINORS` even though he's now active). This does **not** corrupt payroll math — `computeTeamPayroll` sums by CURRENT roster membership, not by the stored `type` label — only a cosmetic per-player label could ever read stale. Phase 5 (Options/Waivers/DFA, which is what actually grants/revokes real roster status) is the natural place to properly handle contract-type transitions.

### 40. 50-man Roster System — Free Agency Economics: Arbitration & Non-Tender — done (Phase 7 of the "50-man Roster System" arc)
Per `player-movement.md`'s "Service Time & Free Agency" section: "arbitration eligibility starts at 3 years, running through the 6th — a player negotiates/arbitrates salary rather than playing for a fixed minimum," plus "non-tender: a controllable pre-free-agency player must be tendered a contract by a set deadline or becomes an immediate free agent."

**This is the first thing in the codebase that legitimately changes an existing player's salary.** `engine/contracts.js`'s `assignMissingContracts` is sticky-once-assigned, and its own header already said "Phase 7 owns real renegotiation" — this is that.

**Research turned up two real missing prerequisites, and the roadmap's own Phase 7 line named both** — confirmed by search, not assumed, and **scoped out with the user before any code was written**:
- **Super Two is not built.** It needs mid-season call-up timing, which this whole-season-block engine can't express — already explicitly deferred back in Phase 4 for exactly this reason.
- **The service-time-manipulation countermeasures (ROY service-time credit, draft-pick compensation) are not built.** Both need an **Awards system that does not exist anywhere** — `engine/hallOfFame.js`'s own header says awards are a zero-weighted case-score extension point precisely because "no awards... system exists." Awards is itself blocked on a *second* gap: per-season stats (`engine/season.js`'s `seasonBattingStatsById`/`seasonPitchingStatsById`) are computed every season but **never reach live state or the React context** — they feed only the offline Hall-of-Fame snapshot pipeline, a limitation §20 flagged deliberately at the time. **Awards is therefore a real future phase**, and building it would also retroactively de-zero the Hall of Fame's own award weighting.

**Arbitration is modeled as a real file-and-trial hearing** (confirmed with the user over the simpler formula-driven-raise alternative). Club and player each file a figure; the arbitrator forms his **own rng-noised read** of the player's value and awards **whichever filed figure sits closer to it — never a midpoint.** That last property is the entire point of the real mechanic: it makes filing an unrealistic number mechanically punished rather than a free roll, and `validate:arb` asserts it directly across 51 different arbitrator draws.

**New `engine/arbitration.js`** — `computeArbitrationMarketValue` is **the real payoff of Phase 4**: it reuses `contracts.js`'s quality curve but drives the service-time term from **real accrued `mlbServiceDays`** rather than that file's age-based proxy. `contracts.js`'s header said outright "Phase 4 is expected to replace this proxy with a real day-accrual signal; not attempted here" — this is the first place it actually happens. **Deliberately scoped to arbitration only, not a retroactive rewrite of `contracts.js`'s proxy**, which would re-value every salary league-wide and invalidate §36's empirically-calibrated `SALARY_FLOOR`/`LUXURY_TAX_THRESHOLD`. Also `fileClubFigure`/`filePlayerFigure` (anchored to **both** current salary and market value), `resolveArbitrationHearing`, `shouldNonTender`, and the `runArbitrationAndTenderSweep` season-boundary sweep.

**Why non-tender fires on the right players rather than at random** — the anchoring is load-bearing, not cosmetic: filings track current salary (sticky, **backward-looking** — money earned by past performance) while market value tracks current quality (**forward-looking**). So the players who fail the test are precisely *declining veterans still being paid for what they used to be* — the real-world non-tender case, emerging from the mechanics rather than special-cased. `validate:arb` proves this discriminates correctly by running two players on **identical $6M salaries** where only current quality differs: the declined one is non-tendered, the productive one isn't.

**An automatic season-boundary sweep, not a per-player UI action** — deliberately unlike Phases 5/6. Arbitration and non-tender fire for hundreds of players simultaneously at a league-wide deadline, so a sweep is the honest model (matching Phases 3/4), and a per-case UI would be a serious per-season clicking burden with no front-office AI to help.

**A real calibration bug, caught by smoke-testing against actual simulated state BEFORE wiring into `data/season.js`** (the arc's own established discipline, and the same class of finding as §36's bimodal-payroll discovery): a first version ramped arbitration leverage 0 → 1 across the window, so a player at exactly 3 years valued at essentially `MLB_MIN_SALARY`. But those players already carry salaries generated by `contracts.js`'s **age**-based proxy — a completely different scale — so current salary routinely exceeded "market value" and **19.3% of all arbitration-eligible players were non-tendered**, several times a realistic rate, gutting rosters every offseason. Fixed at the root by porting real arbitration's actual **40% → 90% escalation shape** rather than by tuning the non-tender threshold around a broken valuation. `NON_TENDER_VALUE_RATIO` was then calibrated empirically against a real 5-season run, with the **whole measured sweep kept in the code comment** (1.30→19.3%, 1.40→12.9%, 1.50→7.9%, 1.70→2.9%) so a future tuner sees the curve, not one number with no context.

**A real crash, caught by this phase's own multi-season integration section — the identical depletion bug Phase 1 hit and recorded.** An early version simply dropped the non-tendered player and left the roster hole; a real 5-season run then died with `Cannot read properties of undefined (reading 'ratings')` deep in game-side construction once a section drained empty. §34's own recorded lesson called this exactly: *"any change that removes an item from a finite, shared, season-persistent pool needs a multi-season stress test, not just a single-transition test — depletion bugs are silent for several iterations before they crash."* Fixed properly: **a non-tender now always fills the vacated spot via a real call-up** (`engine/minorLeagues.js`'s `promoteAndBackfill`, the exact AAA→MLB cascade retiree replacement already uses), and if no replacement can be found anywhere, **the club keeps the player rather than non-tendering him** — realistic on its own terms (no club cuts someone it has nobody to replace) and structurally incapable of reintroducing the bug. Both branches are asserted directly.

**A real knock-on effect on §28's closed-loop free-agent pool — and a claim worth stating precisely rather than optimistically.** §28 flagged `establishedFreeAgentPoolById` as closed-loop and shrinking fast (130 → 16 over 15 seasons) because real free agency's actual source — players reaching the open market — had no analog here. Non-tenders are genuinely that missing source. A 5-season sample looked like a clean reversal (128 → 482), **but the full 15-season run tells a more honest story**: `128, 121, 612, 558, 501, 482, 401, 329, 266, 213, 171, 132, 105, 64, 39, 25`. What non-tenders actually produce is a **large one-time injection, not a permanent fix** — the first cohort of players whose age-proxy salaries are badly misaligned with real service-time value all get corrected at once, after which arbitration keeps salaries tracking market value, fewer players end up overpaid, and the pool resumes draining via retirement. So §28's limitation is **substantially buffered, not solved**; a real ongoing inflow (expiring contracts) still doesn't exist. `validate:freeagency` now asserts exactly this shape — that the pool refills, stays bounded, *and* still drains in the long run — so a future change that accidentally makes it compound forever fails loudly.

**This also invalidated a pre-existing assertion, correctly.** `validate:freeagency`'s section 9 asserted "pool size never increases absent any signings" — true and meaningful when the pool really was closed-loop, and false by design the moment non-tenders exist. The engine was right and the *test* was stale, the same situation §24 hit when the College System deliberately replaced `validate:draft`'s Phase-2-era 100%-sign-rate assumption. Updated rather than worked around — and worth noting it was the full-suite run, not this phase's own script, that caught it.

**A real downstream side effect, found during live verification and flagged rather than quietly shipped — §36's payroll constants are now miscalibrated.** Live at season 3, league-wide payroll reads **$37.4M–$75.3M across all 50 clubs**, against §36's empirically-calibrated `SALARY_FLOOR` of $55M and `LUXURY_TAX_THRESHOLD` of $165M. Two compounding causes, both intrinsic to this phase: arbitration replaces age-proxy salaries with (lower) real service-time-based market values across the whole `[3,6)` window, and the first-season non-tender wave swaps several hundred expensive veterans for minimum-salary call-ups. The luxury tax is now effectively **dead** (nobody approaches $165M) and the floor now catches a large share of clubs rather than the intended ~5-10%. This does not break anything — both thresholds are informational-only with no scripted-event consequence wired to them (§36) — but **re-calibrating them against the post-arbitration distribution is real, named follow-up work**, and should be done the same empirical way §36 did it originally (run the real distribution first, don't hand-pick). Deliberately not attempted here: it belongs with the Financials/CBA system, not bundled into an arbitration phase, and the distribution will shift again once Phase 8's Rule 5 draft and any future Awards phase land.

**`data/season.js`**: the sweep runs in `advanceToNextSeason` only, strictly **after `advanceServiceTime`**, so a player who just crossed 3 years with this season's own credit gets his hearing in that same offseason rather than waiting an extra year. Season 1 returns an empty `arbitrationResult` (service time only starts accruing at the *end* of season 1, so nobody can be eligible yet — the same "nothing to evaluate yet" shape `promotionRelegationSwaps` already uses). **`STATE_SCHEMA_VERSION` 17 → 18** (a new top-level persisted key, so a v17 save genuinely lacks it) — and per §38's hard-learned lesson, all five hardcoded `STATE_SCHEMA_VERSION === 17` script checks were grepped and fixed **proactively, before running the suite.**

**UI — the League Wire, not a new page**, following promotion/relegation's precedent (§21). `getLeagueWireEvents()` gained `arbitration` and `nonTender` entries (a hearing where club and player filed millions apart, and who won, is genuinely good wire copy), both filed at Season Start like promotion/relegation since they resolve in the offseason; `Events.jsx`'s type filter and copy extended to match; plus a `getArbitrationResult()` getter.

Validated via `npm run validate:arb` (`scripts/validate-arbitration.mjs`, 7 sections) — market value proven to read real service time rather than age (a 5-year and 3-year player with **identical ratings and identical age 27** value differently), filing direction and the current-salary anchor, the hearing's never-a-midpoint property plus closer-figure-wins in both directions plus a proof that the arbitrator's noise genuinely produces *both* outcomes (a real hearing, not a deterministic formula), the declined-vs-productive non-tender discrimination above, the sweep touching only the `[3,6)` window (sub-3 and 6+ salaries provably untouched), the no-replacement guard, and a real 5-transition integration run. Full 29-script regression suite green.

### 41. 50-man Roster System — Rule 5 Draft — done (Phase 8 of the "50-man Roster System" arc)
Per `player-movement.md`'s Rule 5 section: "Protects against roster-hoarding — if a club doesn't add a minor leaguer to its 50-man roster within a defined number of minor-league seasons, other clubs can draft him," on the real age-based split (**4 seasons if signed at 19+, 5 if signed younger**). The drafting club "must keep him on the active 26-man MLB roster for the entire following season — he cannot be optioned to the minors — or must offer him back," and the doc is emphatic: *"Worth porting exactly, not simplifying — the 'must stick or get offered back' tension is what makes it work."*

**The best-prerequisited phase in the arc.** `engine/serviceTime.js`'s `isRule5Exposed` was built and fully tested back in Phase 4 but **had never had a production consumer** — this phase is its first, the third time this arc's "build the scaffold now, wire it later" habit has paid off (Phase 5 gave `wasOutrightedBefore` its real input; Phase 7 gave accrued service time its first real use).

**Two research findings, measured against real season-7 state before any design work** (the §36/§40 discipline), each of which changed the approach:
- **4,187 players are Rule-5-exposed** out of 10,249 affiliate players (AAA 444 / AA 646 / A 1,291 / Rookie 1,806). Real Rule 5 drafts pick ~15-20 players *total*, so a naive "everyone exposed is draftable" design would have been absurd — **the draft had to be hard-bounded.**
- **The buried talent is real**, which is the entire justification for the rule existing: the best exposed player rated **46.6** against an active-roster **median of 37.6**.

**Real MLB's own natural bound turned out to be unusable here, and that's a genuinely interesting structural finding.** Real clubs may only select with a 40-man roster opening. But `engine/rosterProtection.js`'s `revalidateAndTopUpReserveRoster` always tops the Reserve pool back to a full `RESERVE_ROSTER_SIZE` (24) out of a 40-player AAA+AA eligible pool — so in this engine **the 50-man is never open**, and porting that gate faithfully would have made the entire draft dead code. Replaced with a bound that fits this engine and arguably models the real incentive better: **a club selects only when the best available exposed player beats its own weakest same-section active player by a real margin** (`RULE5_MIN_UPGRADE_MARGIN`), reusing the same `playerQualityScore` upgrade heuristic `resolveWaiverClaim` and `signEstablishedFreeAgent` already use rather than inventing new AI. That prices a selection against an *active-roster spot*, which is exactly what the doc says the drafting club actually risks.

**The margin was calibrated empirically, not guessed** — measured against a real season-6 state (3,359 exposed, all 50 clubs), with the whole sweep kept in the code comment: margin 0 → 50 picks (avg gain 5.8), 6 → 46 (10.0), 8 → 38 (11.7), **12 → 25 (14.0)**, 15 → 12 (16.1). 12 was chosen because ~25 picks across 50 clubs is the *same ~50% of clubs selecting* that real MLB sees (~15-18 across 30 clubs), with a genuinely meaningful average upgrade instead of marginal churn. At real scale it settles to a stable 39 → 31 → 28 → 27 as the exposed pool works itself out.

**New `engine/rule5Draft.js`** — `findExposedPlayers`, `runRule5Draft` (one round, worst-to-best via `engine/draft.js`'s `computeCombinedReverseStandingsOrder`, one pick per club, never from your own system), and `resolveRule5Obligations`. A selection: the pick joins the active 26; the **displaced incumbent is demoted to the drafting club's own AAA, not released** (he's an org player under contract, so the waiver/free-agency release precedent doesn't fit — this mirrors what really happens when a Rule 5 guy makes the team); and the pick's hole in his original org is **immediately backfilled** via `backfillLevelFromBelow`.

**That backfill was written in from the start rather than discovered by a crash — the first time in this arc that lesson was applied preemptively.** Phase 1 (§34) and Phase 7 (§40) *both* shipped a version that pulled a player out of a finite, season-persistent pool without refilling it, and both crashed several seasons later with the identical `Cannot read properties of undefined (reading 'ratings')`. This phase had the highest depletion exposure of any so far (it removes from affiliate rosters *and* active rosters simultaneously), and `validate:rule5`'s section 6 asserts directly that no affiliate or active section ever drains across 6 real seasons, plus that all 50 clubs still carry exactly 26 players.

**A subtle parsing bug avoided by writing the test first**: club ids are `${teamId}-${LEVEL}`, but real team ids contain hyphens themselves (`alexandria-va-exchange`), so a naive `split('-')` would mis-parse the owning org. `findExposedPlayers` uses `lastIndexOf('-')`, and section 1b asserts it against a real hyphenated id.

**The "must stick or be offered back" tension — the part the doc insists on porting exactly** — is where this phase integrates with Phase 5 rather than living alone: `optionPlayerToMinors` now **refuses a Rule 5 pick outright**, and `designateForAssignment` on one resolves as a real fourth outcome, **`RETURNED_TO_ORIGINAL_CLUB`**, instead of running waivers. Since this engine has no mid-season roster moves, sticking is the default in pure auto-play (100% stick rate observed) — the interesting cases come from genuine commissioner action, which is exactly where the tension belongs. `TeamDetail.jsx`'s action button reads **"Return" instead of "Option"** for these players rather than offering a button that would silently do nothing.

**`data/season.js`**: `resolveRule5Obligations` runs first (clearing *last* year's picks) then `runRule5Draft`, both in `advanceToNextSeason` after `advanceServiceTime` (so exposure reflects the season just credited) and before the arbitration sweep. **`STATE_SCHEMA_VERSION` 18 → 19** — a new persisted `rule5Result` key *and* a new `rule5` field on every `serviceRecord`, exactly the two-part shape change §38's bug was about; all hardcoded script checks were grepped and fixed proactively before running anything.

**UI**: a third section on `pages/Draft.jsx` (which already hosts the domestic and international drafts — the obvious home, no new route) showing each pick with its drafting *and* original club, plus how last season's picks resolved; `rule5` League Wire entries; and a quiet `R5` tag on `TeamDetail.jsx` matching the existing tag convention.

Validated via `npm run validate:rule5` (`scripts/validate-rule5.mjs`, 7 sections, 33 checks, **all passing first run**) — exposure gating, hyphenated-id parsing, the margin gate proven in both directions, a selection's full effect including the asserted backfill, own-system exclusion, all three obligation branches (option refused, DFA returns him, sticking clears it, and a same-season pick correctly *not* resolved yet), and the real multi-season no-drain integration run. Full 30-script suite green.

### 42. 50-man Roster System — Player Rights — done (Phase 9 of the "50-man Roster System" arc)
The roadmap names three rights; research found **only two were actually unbuilt**. **Outright refusal rights were already done** — Phase 5 wired `isOutrightRefusalEligible` into `designateForAssignment`'s real `REFUSED_FREE_AGENCY` outcome, and `validate:ows` already covers it. What was left: **10-and-5 no-trade rights** and **minor-league free agency**, both of which had `engine/serviceTime.js` functions with **zero production consumers**.

**10-and-5 rights close the last outstanding Phase 4 scaffold.** `isTenAndFiveEligible(serviceRecord, consecutiveYearsWithCurrentOrg)` took that second argument as an external param precisely because nothing tracked it; `serviceRecord.consecutiveSeasonsWithOrg` finally makes it real. Confirmed with the user: consent is a **real roll weighted by whether the acquiring club is actually better** (`computeNoTradeConsentProbability`, comparing average `playerQualityScore` of both active rosters — a signal already passed to `executeTrade`, so no new plumbing), not a hard block. Truer to life, since real 10-and-5 veterans frequently *do* waive; a flat veto would remove every veteran from the trade market permanently and never produce a decision. A refusal returns `NO_TRADE_REFUSED` with **no map touched**, exactly like the existing `MEDICAL_REVIEW_FAILED` branch.

**Org-continuity tracking is deliberately in ONE self-correcting place rather than five patches** — the design decision worth remembering here. A player's org changes via trades (Phase 6), waiver claims (Phase 5), the Rule 5 draft *and* its returns (Phase 8), and free-agent signings — five sites today, and a sixth whenever a future phase adds a transaction type. Instead of a reset call at each, `advanceServiceTime` (which already walks every org player each season) **compares his current `teamId` against the `lastOrgTeamId` stored at the previous sweep**: same org increments, different resets to 1. That catches every existing *and* future org change for free, and is exactly the kind of bookkeeping that silently rots when it depends on five unrelated call sites remembering it. `validate:rights` proves it by driving a reset through a **real `executeTrade`**, not a hand-set field.

**New `engine/minorLeagueFreeAgency.js`** — per the doc, "distinct from Rule 5... this is about a player *walking on his own*." Confirmed with the user: minor-league free agents get **their own dedicated pool**, matching §28's reasoning for keeping College, International, and Established separate — a career minor leaguer (measured average age 32-33) is a genuinely distinct population. They sign to an affiliate by quality via the existing `signAmateurFreeAgent`, which is the right destination, unlike the established pool's straight-to-MLB path.

**A required smoke test before wiring changed the design outright** (the §36/§40/§41 rule, now firmly a habit): **3,058 players qualify by season 7, growing to 5,789 by season 10.** Releasing every eligible player each season would mean thousands of simultaneous departures and thousands of backfill cascades. The cause is structural — eligibility is *permanent*, so the set accumulates rather than clearing. The fix is also the realistic one: in real baseball the large majority of minor-league free agents **re-sign with their own organization**, so `MINOR_LEAGUE_FA_DEPARTURE_RATE` models exactly that. Measured result: **~470-510 walk per season** against 3,000+ eligible, the backlog drains gradually instead of in one shock, and no artificial cap was needed.

**Backfill went in from the start again** (`backfillLevelFromBelow`), the third consecutive phase removing players from finite, season-persistent affiliate rosters. Verified across 8 real seasons: no affiliate or active section ever drains, and all 50 clubs still carry exactly 26.

**Two real traps hit while writing the validate script, both worth recording because they're repeatable:**
- **The `() => 0` / `gaussianRandom` infinite hang — hit for the SECOND time** (first in §18). A departure triggers `backfillLevelFromBelow` → `generateForLevel` → `gaussianRandom`, whose `while (u === 0) u = rng()` spins forever on a constant-zero rng. Symptom is nasty: the script hangs with **no output at all**, because output is buffered, so even the sections that already passed stay invisible. Since it has now bitten twice, the rule was **promoted out of §18 into "Key conventions"** with the specific function names that reach it.
- **A single constant rng cannot satisfy two opposite-direction checks.** `executeTrade`'s consent roll wants a LOW draw (`rng() >= consent` refuses) while the medical review wants a HIGH one (`rng() < failureRate` fails), so `() => 0.0001` made the veteran waive and then immediately fail his physical. Fixed with a sequenced rng. Worth remembering whenever a function's rng feeds more than one gate.
- Also, a third: an early check asserted retirements at `rng() = 0.5` and saw none — `retirement.js`'s established curve is genuinely gentler than the amateur curves. **The test's expectation was wrong, not the engine**, and it was rewritten as a directional check (43-year-olds retire, a 24-year-old survives the same pass) rather than a magic number.

**`data/season.js`**: the sweep runs after `advanceServiceTime` and **after the Rule 5 draft on purpose** — a player just taken in Rule 5 is now protected, so he's correctly no longer eligible to walk in the same offseason. **`STATE_SCHEMA_VERSION` 19 → 20** (new `minorLeagueFreeAgentPoolById` + `playerRightsResult`, plus two new `serviceRecord` fields), all hardcoded script checks fixed proactively per §38.

**UI**: a 4th pool tab on `FreeAgents.jsx` (its description corrected — the established pool is no longer fully closed-loop now that non-tenders feed it), a quiet `10-5` tag on `TeamDetail.jsx`, and `minorLeagueFA` wire entries **capped at 15 plus an "…and N more" line** — hundreds walk per offseason and an uncapped list would drown out every other event type.

Validated via `npm run validate:rights` (`scripts/validate-player-rights.mjs`, 8 sections) — org continuity through a real trade, both halves of the 10-and-5 gate, consent direction and clamping, a refused trade leaving every map untouched (plus the same veteran going through once he waives, and a non-10-and-5 player never being asked at the same rng draw), eligibility/departure/**asserted backfill**, the majority-re-sign bound, pool pruning on the real curve, and an 8-season no-drain integration run. Full 31-script suite green.

### 43. 50-man Roster System — Injury Rehab Assignments — done (Phase 10, the FINAL phase, of the "50-man Roster System" arc)
Per `player-movement.md`: "a player on the MLB injured list can be sent to a minor-league affiliate for live game reps before officially activating" — **position players up to 20 days, pitchers up to 30**, and it **does not use an option**.

**A real modelling problem had to be solved before the mechanic could mean anything.** Rehab exists so a player is *ready* on activation — but this engine had no rust or ramp-up penalty for a returning player, so there was nothing for readiness to offset and the whole phase would have been cosmetic bookkeeping. Confirmed with the user, taking the more ambitious of the options offered: **build the return-rust penalty first, then let a rehab stint offset it.** That also closes a gap flagged since §8, which named `consistency.js`'s `withPerformanceModifiers` as "the natural primitive to reuse" for exactly this family — reused here rather than reinventing a rating-shifting helper.

**Necessarily automatic and in-season, not a UI action** like Phases 5/6's Option/DFA/trade buttons: injuries exist only inside `simulateGamesIntoState`'s per-game loop, and `state.seasonResult` is a season that has *already finished*, so there is no in-progress season a live action could reach. Same class of constraint as Super Two.

**New `engine/rehabAssignment.js`** — rust is derived from the severity tier (`SHORT_TERM_IL`/`LONG_TERM_IL` only; day-to-day is too short and season/career-ending never return), peaks at `MAX_RUST_PENALTY` on the first game back and decays to zero, and applies to **pitching attributes for pitchers, physical hitting/baserunning/defense for everyone else** — mirroring `applyFatigue` exactly. Threaded through the identical path fatigue already uses: new `rehabStatusById`/`rustStatusById` season-state Maps → `buildGameSide` → the side object → applied in `createSide` right where `applyFatigue` sits. No new plumbing pattern invented. The player is **not physically moved** between roster arrays during a stint — he's already excluded by the injury, so relocating him would add real depletion risk (the §34/§40/§41 bug this arc hit three times) for zero behavioural gain.

**The calibration smoke test caught that the mechanic was completely inert, which is the most instructive part of this phase.** At the first values (`RUST_REMOVED_PER_REHAB_GAME = 1.0`, every eligible player automatically rehabbing), a real 150-game season produced **130 activations of which 130 had rust fully erased** — every rehab-eligible player serves ~13 games against at most 14 rust games, so **the penalty literally never applied to anyone**. The phase would have shipped looking complete while doing nothing. Two changes fixed it, and both are more realistic than what they replaced: `RUST_REMOVED_PER_REHAB_GAME` dropped to 0.6 so a stint leaves a real residue, and `REHAB_ASSIGNMENT_PROBABILITY` (0.55) reflects that **not every club gets every eligible player out for live reps** — which is what creates the observable contrast the mechanic depends on. The decision is made **once per injury and remembered** via a `declined` sentinel in the same Map; re-rolling each game would make almost everyone eventually rehab and collapse straight back to the inert case.

Measured before/after at real scale:

| | rust inert | rust active (shipped) |
|---|---|---|
| stints started | 142 (all eligible) | 61 (~54%, matching the 0.55 rate) |
| avg rust carried on return | **0.0** | **4.1** |
| activations fully erased by rehab | 130/130 | 11/112 |
| runs/game | 7.45 | **7.36** |

**The run-environment cost is −0.09 runs/game (~1.2%)** — and by CLAUDE.md's own distinguishing question (is a fixture behaving unrealistically, or is a real mechanic legitimately consuming production?), this is squarely the second: a recently-activated player performing slightly worse is the mechanic working. `validate:game` is **unchanged at 8.94/8.54** because its fixtures pass no rust Map, which also confirms the additive-default guarantee holds for every existing caller.

**A real wiring bug caught by the suite, not by inspection**: `simulateGamesIntoState` destructures its accumulators from `seasonState`, and adding the new Maps to `createSeasonState`'s return without adding them to that destructuring crashed `validate:season` with `ReferenceError: rehabStatusById is not defined`. They're now destructured **with defaults**, so a hand-built fixture that doesn't carry them still works. Separately, `engine/ledgerCup.js`'s `simulateSeasonWithCup` builds its own `seasonResult` object — the three new fields had to be added there too, or the data would have existed during simulation and then silently vanished on the path `data/season.js` actually persists (the exact `cupState` gap §33 had to fix).

**`STATE_SCHEMA_VERSION` 20 → 21**, all hardcoded script checks fixed proactively per §38.

**UI, with an honest caveat about one half of it.** The **League Wire is the real surface** for this mechanic and works well: capped `rehab` entries carrying real in-season game numbers (unlike Phases 7-9's offseason entries), showing the contrast directly — *"activated after a 9-game rehab assignment, still shaking off 1 game of rust"* vs. *"activated straight off the injured list with no rehab stint — carrying 6 games of rust."* There's also a `Rust · Ng` tag on `TeamDetail.jsx`, deliberately distinct from `InjuryTag` since a rusty player is *available*, just not yet himself — **but it will almost never actually render**, and that's a real limitation worth stating rather than glossing: `rustStatusById` is an END-OF-SEASON snapshot, and rust lasts only 1-14 games, so it has essentially always decayed away by the final game. Verified live: 2 injury tags rendered (injuries run 10-60 games and survive to season end) and 0 rust tags, on a season whose wire showed 15 real activations. This is the same class of partial-picture limitation §19 already documents for the injury feed, and it would only be fixed by the day-by-day simulation model the user has separately flagged as a future direction.

Validated via `npm run validate:rehab` (`scripts/validate-rehab.mjs`, 7 sections) — severity gating, the penalty peaking then decaying to exactly zero, `applyReturnRust` lowering real ratings on the right attribute set and proven non-mutating, the 20-vs-30 split (a pitcher 25 games out is eligible where a position player isn't), **the core claim that a rehab stint measurably beats no stint**, a direct assertion that `standardOptionYearsUsed` is untouched, and a real-season section measuring rehabbed vs. cold returners (**0.9 vs 7.1 games of rust**) with a runs/game guard. Full 32-script suite green.

### 44. Individual Season Awards — done (new scope, the first phase after the 50-man Roster arc)
`awards-and-hall-of-fame.md`'s award slate, none of which existed. `engine/hallOfFame.js`'s header had said since §18 that awards were a zero-weighted case-score extension point *precisely because* "no awards... system exists," and the 50-man arc's Phase 7 had to defer its ROY service-time credit and draft-pick compensation for the same reason. **Confirmed with the user: build the full slate — majors, Silver Slugger, and the milestone-naming mechanic — in one phase, infrastructure included, dropping nothing that hadn't been started.**

**A research finding that corrected my own earlier claim, and halved the infrastructure.** I had recorded (and told the user) that per-season stats "never reach live state." More precisely: `seasonBattingStatsById`/`seasonPitchingStatsById` **are** persisted — they arrive *inside* `seasonResult`, so grepping `data/season.js` for the bare names finds nothing. They were persisted but never **exposed**, the identical live-but-unexposed gap §33 had to close for `cupState`. Only a getter was needed. The genuinely absent piece was the **Writers Corps**, which existed solely inside the offline Hall-of-Fame pipeline.

**Reuse over reinvention, throughout.** `engine/hallOfFame.js`'s `simulateWriterVote` already models Traditionalism/Homerism/Contrarianism against a real Writer's sliders, so award candidates are shaped to its own `{caseScore, clearedMilestone, primaryTeamId}` contract instead of growing a second voting system. `engine/hotColdStreaks.js`'s real-MLB-anchored `WOBA_WEIGHTS` was **exported** to score a full season's offensive line rather than defining a second, drift-prone composite. `engine/leagueProgression.js`'s private `advanceWritersCorps` was **exported** rather than duplicated — the same "export the helper" precedent as `eligiblePlayersForTeam`/`candidatesForSigning`. **A calibration bug that made the electorate decorative — caught by smoke-testing, and the most instructive part of the phase.** Award scores live on a completely different scale from Hall-of-Fame case scores, so candidates are normalised into `simulateWriterVote`'s band before voting. At my first spread (30), the best candidate landed at case score 100, and that function's own `0.5 + (caseScore - 70)/40` clamps to certainty — so **every single award was unanimous at 100%**, and the writers' Homerism/Contrarianism sliders could never change an outcome. The vote existed and did nothing, which is exactly the "reuse the Writers Corps" premise defeated. At spread 12 the field spans roughly 0.8 down to 0.2 vote probability: real, contested races (measured 69-84% winning shares) that a homer-heavy or contrarian corps can genuinely swing.

**Real emergent correctness worth locking down**: Exchange fields all 9 Silver Sluggers but **Foundry only 8 — it's the no-DH league**, so no Foundry player ever accumulates DH plate appearances and there is correctly no Foundry DH award. Nothing special-cases this; it falls out of the league's own DH rule. `validate:awards` asserts it directly.

**The milestone-naming mechanic is built in full, including the subtle part.** An award is permanently renamed after the first player to win that *slot* three times — scoped per slot, so MVP-Foundry and MVP-Exchange name independently, as do all 17 Silver Slugger slots. Once locked in it **never changes**, even for someone who later wins more (the doc is explicit, citing the Cy Young). The doc's alternate statistical-dominance path is **sequenced, not simultaneous** — it unlocks only once a slot has been given out 10 times AND only if nobody has already locked in three wins; a third win before the 10th giving renames it permanently and the 2-SD path never becomes relevant for that award at all. My plan had wrongly assumed this path was unspecced and deferred it; re-reading the doc showed it fully specified, so it was built. Verified firing at real scale: 3 slots permanently named within 5 seasons.

**Deliberately NOT built, each with a real named blocker** (recorded rather than faked, per the user's "don't forget anything we haven't started"):
- **Gold Glove** — §14 built defense as a *team-level composite* with no per-fielder attribution, so **no per-player fielding stats exist at all**. There is literally nothing to vote on.
- **Finals MVP** — `engine/playoffs.js`'s `simulateBestOfSeries` discards each game's box score (keeping only runs and injuries), so no per-player postseason stats exist.

## Key conventions

- **Every numeric constant is an explicit, commented placeholder** ("needs real playtesting") — a deliberate tone across the whole engine, not sloppiness. Don't hesitate to add more of these; don't try to "finalize" a number without being asked to.
- **`rng` is always an explicit parameter**, never an implicit `Math.random()`.
- **One-concern-per-file**, composed by a thin orchestration layer (e.g. `pitcherFatigue.js` + `timesThroughOrder.js` → `pitcherDegradation.js`; `growthModel.js` + `positionReassignment.js` + `reassignmentReaction.js` → `development.js`).
- **"Never returns" / one-time-use invariants** (bullpen, bench, injured-player exclusion) are enforced both structurally *and* defensively. Stress-test any new invariant like this at real scale before trusting it.
- **Extension-point pattern** for systems that don't exist yet, rather than building them prematurely (`locationModifier` / `injuryImpact` on `growthModel.js`).
- **Tailwind gotcha, hit twice already**: `` `grid-cols-[${var}]` `` template-literal interpolation breaks Tailwind's static class scanner — the *complete* class string must appear literally in the source file (a `const X = 'grid-cols-[...]'` declaration is fine and gets picked up; interpolating a variable *into* the brackets at the point of use is not). When in doubt, hardcode the literal class string at every JSX use site, matching `BoxScore.jsx`'s verbose-but-safe pattern.
- **`EnterPlanMode`** for any genuinely new system with real design decisions to negotiate (used for every major build-order step above); skip it for well-precedented extensions of an already-approved pattern.
- **Never pass `() => 0` as a "force everything" rng if the code path can reach `gaussianRandom`** (player/manager generation, growth variance, scout error, Temperament/Streak-Read noise, and **anything that generates a replacement player — `generateForLevel`, `promoteAndBackfill`, `backfillLevelFromBelow`**). `gaussianRandom` has `while (u === 0) u = rng()` and spins **forever**. Use a small nonzero constant (`() => 0.0001`) instead. Safe only for a bare `rng() < probability` comparison. First hit in §18 (Hall of Fame), **re-hit in §42's own validate script** — a sweep whose departures triggered backfills — so this is a genuinely repeating trap, not a one-off. Symptom: the script hangs with no output at all (output is buffered, so you don't even see the sections that already passed).
- **Trace calibration drift to its root cause** before touching a shared/anchored constant — see below.

## Calibration notes — read before touching any of these

Several systems were jointly tuned and need re-validation together if any one changes:

- `plateAppearanceConstants.js` (real-MLB-anchored — **do not** inflate to fix an aggregate run-environment issue elsewhere), `pitcherFatigue.js`, `pitchingChanges.js`, `timesThroughOrder.js` — target ~8.6-9.0 runs/game, ~4.3-4.6 runs/team/game, but only in `validate:game`'s **symmetric average-vs-average** matchups.
- Real teams (`realLeague.js`) have wide, independently-randomized per-player quality — mismatched-quality games naturally run lower-scoring than the symmetric baseline (~7.5-8.5 runs/game in `validate:season`, a *loose* sanity bound, not the tight symmetric-matchup target). This is expected, not a bug — don't chase it by inflating PA constants.
- `validate-game-loop.mjs`'s own synthetic bullpen fixture uses a realistic role-based quality curve (`BULLPEN_QUALITY` — Long/Middle weakest, Closer best), not a flat quality bullpen — this was the actual fix for an earlier "saves are too rare" investigation. Don't revert it.
- Starter pitch counts should land around 85-107 (stamina-dependent), not the 120-146 an earlier tuning pass allowed. If they creep up again, fix `pitchingChanges.js`'s pull thresholds directly — don't loosen them back up just to hit a run-environment number; find that fix elsewhere (see the bullpen-quality-curve precedent above).
- Injury setback rate: **never** use a flat per-game-check hazard for an injury's *entire* duration — it compounds explosively with tier length (a 3%/check hazard over a 60-game floor is ~84% cumulative, not "some players have setbacks"). Bound the window (`SETBACK_WINDOW_GAMES`) instead.
- `createPlayer()` defaults `bats`/`throws` to `'R'` — any synthetic engine fixture that doesn't explicitly randomize handedness (via `playerGenerator.js`'s exported `pickBats`/`pickThrows`) is an implicit same-handed matchup, which now reads as a systematically *harder* matchup than a realistic mixed-handedness roster since platoon splits exist. Caught this exact issue in `validate-game-loop.mjs` (see Platoon splits section) — check any *new* synthetic fixture for this too.
- Stolen bases and bunting both trade a small amount of run environment for realism — caught-stealing removes baserunners, sacrifice bunts trade a guaranteed out for one base (a real, lower-expected-value play in most situations, matching real sabermetric consensus). `validate:game`'s runs/game has drifted modestly downward across both additions (~8.24/8.46 baseline → ~7.94/8.32 after bunting) — **expected**, not a regression to chase, unlike the handedness-fixture bug above. The distinguishing question when a number moves: is a fixture behaving unrealistically (root-cause and fix it), or is a real mechanic legitimately consuming outs/bases it didn't before (document it and move on)?
- Fielding/positioning reversed that trend: `validate:game`'s runs/game rose from ~7.94/8.32 to ~8.96/8.79. Not a regression — the groundout-scoring fix (`baserunning.js`'s `resolveOut`) closed a real gap where a runner on third could **never** score on a routine groundout, in any prior session. That was suppressing runs every session up to this one; fixing it was always going to raise the number, and it landed back inside the ~8.6-9.0 reference band rather than outside it. Team-defense-driven BABIP/error/no-doubles/infield-in effects partially offset it but don't reverse the direction. Confirmed via `validate:fielding`'s own directional asserts, not just the aggregate move.
